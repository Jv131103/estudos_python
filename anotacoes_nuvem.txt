            Explorando o mundo da computação em nuvem

O termo “nuvem” é amplamente utilizado atualmente nas empresas, 
instituições de ensino, noticiários e até mesmo nas conversas 
informais. No entanto, é necessário definir alguns conceitos 
fundamentais para evitar ambiguidades, distinguindo soluções para 
evitar ruídos de comunicação.

Segundo a AWS Academy (2024), a computação em nuvem pode ser 
definida como: “Entrega sob demanda de poder computacional, banco 
de dados, aplicativos e outros recursos de TI pela internet com 
uma definição de preço conforme o uso”.

Portanto, podemos “alugar” o poder computacional de um grande 
conjunto de computadores, por um tempo definido, pagando somente 
pelo tempo ou quantidade de solicitações a um determinado serviço.

Historicamente, o termo “Computação em nuvem” foi utilizado pela 
primeira vez em uma palestra do professor Rammnath Chellappa em 
um curso de sistemas de informação.

O conceito de nuvem começou a ganhar força em 2003, quando dois 
funcionários da Amazon, Chris Pinkham e Benjamin Black, apresentaram
um paper interno de como a infraestrutura de máquinas da empresa 
poderia funcionar. Eles sugeriram usar parte dessa infraestrutura 
para venda de serviços e prepararam um case para isso.

                Arquitetura de nuvem

Podemos ter diferentes tipos de arquitetura de nuvem, cada uma com 
características específicas que se adequam às necessidades de negócio 
e consideram restrições técnicas das empresas.

De maneira mais ampla, as empresas podem ter os seguintes tipos de 
nuvem:

    Nuvem pública;
    
    Nuvem privada;
    
    Nuvem híbrida.

Na nuvem pública, podemos contratar diferentes serviços de provedores
distintos (AWS, Azure, GCP etc.), incluindo serviços de computação na
nuvem que replicam a infraestrutura de máquinas e rede de toda a 
empresa. Portanto, neste modelo, a empresa não precisa se preocupar 
em gerenciar um parque de máquina localmente, “alugando” servidores 
na nuvem e realizando pagamentos sob demanda. Algumas vantagens 
deste modelo incluem a escalabilidade, e o menor tempo de 
configuração de máquinas, levando a um menor tempo de implantação 
(time-to-value) de novos serviços aos clientes desta empresa. No 
entanto, os mesmos provedores que reservam espaço para a empresa, 
podem alugar o espaço não utilizado para outras empresas.

Na nuvem privada, a infraestrutura é dedicada a uma única 
organização, podendo ser gerida internamente, em uma infraestrutura 
local (on-premises) ou em um datacenter exclusivo. Portanto, existe 
um controle maior ao hardware da empresa contratante. Este modelo é 
ideal para empresas que exigem um maior nível de segurança.

No modelo de nuvem híbrida, as empresas usam a nuvem pública para 
tarefas menos sensíveis, enquanto mantém as aplicações mais 
restritas na nuvem privada, combinando as vantagens de cada modelo 
de contratação.

Ainda é possível combinar diferentes provedores de serviços de nuvem 
pública, no que chamamos de ambiente multi-cloud. Nesta configuração, 
opta-se por parte da infraestrutura em um provedor e parte em outro 
provedor de nuvem, havendo a integração entre os ambientes de nuvem 
por meio de APIs e demais serviços.

                Modelos de serviços em nuvens

Existem basicamente três principais modelos de entrega de serviços
pela nuvem, como infraestrutura como serviço (Infrastructured as a 
Service — IaaS), plataforma como serviços (Platform as a Service — 
PaaS) e software como serviço (SaaS).

Cabe ressaltar que existem variações destes termos que surgiram para 
fins específicos, como banco de dados como serviço (Database as a 
Service — DbaaS), Game as a Service (GaaS), entre muitas outras 
variações.

De acordo com o modelo de serviço em nuvem contratado, podemos ter 
um controle maior sobre a gestão do hardware e do software, ou 
podemos usar um modelo em que podemos focar em questões inerentes ao 
negócio, sem nos preocupar com detalhes de configuração do hardware 
ou do sistema operacional. Os principais modelos de negócio são:

    Infraestrutura como Serviço;

        No modelo de infraestrutura como serviço, há um controle 
        maior sobre o hardware contratado. Este é o modelo mais 
        tradicional em que podemos, por exemplo, alugar uma máquina 
        virtual na nuvem, selecionando recursos como CPU, memória, 
        HD, recursos de rede, assim como o sistema operacional a ser
        instalado nestas máquinas.

        No modelo IaaS, precisamos gerenciar as atualizações do 
        sistema operacional e demais configurações necessárias para 
        atender à nossa demanda. Por exemplo, se formos hospedar um 
        website, teremos que cuidar de toda a parte de instalação de
        um servidor web, até a implantação (deploy) dos arquivos do 
        website.

        Na AWS, podemos citar alguns dos serviços de computação que 
        são inseridos no modelo IaaS, como a criação de máquinas 
        virtuais, com o serviço conhecido como o serviço do Elastic 
        Compute Cloud (EC2), armazenamento em bloco, arquivos ou 
        objetos (AWS Simple Storage Service — S3) e serviços de 
        infraestrutura de redes.

        Portanto, há uma ampla gama de cenários de uso do modelo 
        IaaC para servirem como base para a infraestrutura 
        operacional de uma empresa. Uma empresa ou startup pode, com 
        apenas alguns cliques, definir uma infraestrutura básica 
        para iniciar sua operação, sem se preocupar com quesitos como
        licenciamento de software, espaço destinado a servidores, 
        refrigeração de máquinas, além dos custos operacionais de 
        pessoal especializado.
    
    Plataforma como Serviço;

        No modelo de plataforma como serviço, a ideia é ter um 
        controle menor sob o hardware, focando em questões como 
        implantação de aplicações, eliminando a necessidade de 
        gerenciamento de hardware e infraestrutura subjacente, 
        como configurações de rede. Há, portanto, uma abstração 
        das complexidades inerentes ao processo de configuração, 
        manutenção e escalabilidade de hardware. O serviço AWS 
        Elastic Beanstalk é um exemplo de serviço que foi 
        desenvolvido para facilitar o deploy de aplicações.
    
    Software como Serviço.

        No modelo de software como serviço, busca-se acessar 
        aplicações prontas por meio da internet. Podemos citar 
        diversos serviços existentes, como armazenamento de dados 
        online, como o Google Drive, uso de softwares de escritório,
        como o Microsoft Office 365, aplicações de edição de imagem 
        online e vários outros serviços. Neste modelo, paga-se uma 
        assinatura para uso do software por um determinado período 
        de tempo.

        O Amazon Chime da AWS é um exemplo de SaaS, oferecendo um 
        ambiente para agendamento e realização de videoconferências 
        online.

                            Console

O primeiro acesso à AWS normalmente é realizado pela internet por 
meio do que chamamos de console, disponível em 
https://console.aws.amazon.com/ mediante cadastro inicial. O 
cadastro inicial no ambiente real da AWS é feito após informar um 
endereço de e-mail e a inclusão de dados pessoais e de cobrança 
(cartão de crédito). Lembrando que NÃO É NECESSÁRIO se cadastrar 
neste ambiente, dado que usaremos o ambiente acadêmico (aws academy).

Inicialmente há um período de testes de 12 meses para alguns 
serviços básicos, chamado de free tier, contendo serviços de 
computação (EC2, Lambda, S3 etc.), armazenamento, banco de dados 
e até mesmo serviços de Machine Learning. No entanto, deve-se ter 
atenção ao período de testes, pois ao término do período, os 
serviços implantados não são automaticamente destruídos, podendo 
haver cobranças.

Após o acesso ao console da AWS, é possível escolher o serviço 
desejado clicando no menu superior de serviços ou digitar em uma 
caixa de busca no próprio site.

Depois de criar a conta na AWS, é possível ainda baixar a interface 
de linha de comando para acesso programático à AWS, para que acessos 
subsequentes à AWS sejam feitos sem a necessidade de abrir um 
navegador da internet.

            Interface de linha de comando

Outra forma de acesso é por meio do AWS CLI (Command Line Interface),
que permite executar comandos em um terminal (shell) para tarefas 
comuns, como a listagem de serviços disponíveis, configuração de 
serviços, implantação e demais opções disponíveis. Podemos optar por 
esta opção quando temos alguns scripts prontos para executar ou para 
ganhar agilidade em alguns processos.

A instalação é muito simples, bastando acessar a documentação da AWS
disponível no site https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html, 
e selecionar o instalador de acordo com seu sistema operacional. 
Inicialmente é necessário configurar o cliente do AWS CLI, gerando 
uma chave de acesso pelo serviço da AWS IAM (falaremos mais adiante) 
e configurando o acesso no AWS CLI.

A sintaxe para a listagem e execução de serviços é:

    aws <serviço> <comando> <subcomando> [parâmetros]

No exemplo a seguir, ilustramos alguns comandos executados no CLI 
para listagem de um repositório de objetos (também chamado de bucket)
e, em seguida, do conteúdo do repositório.

    $ aws s3 ls
    2024-09-02 13:26:24 minhascredenciais-meu-bucket

    $ aws s3 ls minhascredenciais-meu-bucket
    2024-09-02 13:27:51          5 meuarquivo.txt

Há também uma versão online do CLI no próprio console da AWS chamado 
de CloudShell.

Este terminal (shell) já está pré-autenticado no ambiente da AWS, e 
permite executar quaisquer comandos disponíveis no AWS CLI.

                Acesso programático

Além dos acessos via console e via CLI, é possível utilizar as 
bibliotecas disponíveis para desenvolvedores para acesso 
programático (SDK). Por exemplo, é possível desenvolver aplicações 
usando o Python.

Por exemplo, a biblioteca chamada boto3 permite acessar 
programaticamente os serviços da AWS por meio de códigos 
customizados, como um notebook em Python.

Desta forma é possível customizar aplicações que consumam serviços 
diretamente da AWS de forma transparente. É possível, por exemplo, 
ter uma estrutura híbrida, com uma aplicação em um servidor local 
(on-premises) e o banco de dados na nuvem (cloud) usando o SDK da 
AWS.

                        Segurança

A AWS conta com diversos recursos para gerenciamento e controle de 
segurança para garantia de acesso aos serviços da nuvem somente por 
pessoas autorizadas. O AWS Identity and Access Management (IAM) é um 
serviço de identificação e controle de acesso que permite definir 
políticas de segurança, utilizando o conceito de privilégio mínimo, 
ou seja, o usuário administrador da conta da empresa na AWS deve 
atribuir explicitamente permissões a um usuário, grupo de usuários, 
política IAM ou função IAM (IAM role).

    IAM User: conta de uma pessoa ou aplicativo com login e senha na 
    AWS.
    
    IAM Group: um grupo de usuários que compartilham as mesmas 
    permissões e autorizações. Os grupos são utilizados para 
    simplificar a concessão e o gerenciamento de permissões dentro 
    de um ambiente. Exemplos de grupos comuns: desenvolvedores 
    (devs), equipe de infraestrutura, testers e administradores 
    (admins). Atribuir permissões a grupos, em vez de usuários 
    individuais, reduz o risco de erros e facilita a manutenção de 
    políticas de acesso.
    
    IAM Policies: documento que define quais recursos podem ser 
    acessados e o nível de acesso a cada recurso.
    
    IAM Roles (Funções): os papéis podem armazenar diferentes 
    acessos e serem temporários. Não precisam de login e senha 
    e podem ser associados a serviços ou usuários. Por exemplo: 
    acesso ao EC2, S3 e demais serviços da nuvem.

No IAM definimos quem (usuário, grupo ou role)  pode acessar um 
recurso, quais recursos  poderão ser acessados e como  serão 
acessados.

                Estimativas de custos

Custo total de propriedade:

    Antes de realizar a migração para um ambiente em nuvem, é 
    importante realizar comparações em relação a um ambiente 
    on-premises. Por exemplo, para utilizar um servidor de 
    aplicações em um ambiente local, precisamos considerar os 
    custos com servidores e licenças de software, além de custos 
    de instalação, energia elétrica, refrigeração dos equipamentos 
    e de até mesmo do espaço físico reservado aos equipamentos de 
    hardware.

    É preciso considerar também os custos com hardware para 
    armazenamento dos dados (por exemplo: discos de armazenamento), 
    rede (switches, cabeamento, firewall etc.), administração da 
    rede e os custos operacionais para manter a estrutura 
    funcionando, incluindo manutenções de hardware e software 
    (por exemplo: patches de correção).

    Realizado o levantamento dos custos locais e do tempo para 
    implantar a infraestrutura local, é possível calcular os 
    mesmos recursos alocados na nuvem, utilizando calculadoras 
    fornecidas pelos próprios servidores de nuvem.

A AWS fornece uma calculadora de preços online 
https://calculator.aws/#/ para tal finalidade.

Pode-se escolher entre uma ampla gama de serviços, definindo-se 
a região onde serão armazenados ou processados, além de haver um 
filtro para localização dos serviços.

Existem diferentes planos para os serviços, incluindo descontos em 
planos de longa permanência.

Comparando-se os custos locais com a estimativa online, é possível 
tomar uma decisão sobre o uso da nuvem. É preciso reforçar que a 
questão de se ter uma máquina pronta em poucos minutos, é difícil 
de mensurar e pode ser crucial para alguns negócios.

    Do Local a Nuvem: Replicando infraestrutura na AWS

Regiões, Zonas de Disponibilidade e VPCs:

    Para disponibilizar serviços de computação em nuvem, a 
    AWS (Amazon Web Services.) mantém centenas de milhares 
    de servidores em datacenters geograficamente distribuídos. 
    Somente em um data center, existem aproximadamente entre 50 
    a 80 mil servidores.

    Para manter o ambiente seguro, evitando falhas e garantindo a 
    recuperabilidade, a AWS usa no mínimo dois conjuntos de 
    datacenters, podendo chegar até 10 datacenters. Este 
    agrupamento de datacenters é denominado de Zona de 
    Disponibilidade (Avaiability Zone — AZ). Estes datacenters são 
    conectados por redes de alta performance para garantir 
    espelhamento dos dados, por exemplo.

    Ainda, para garantir a latência e disponibilidade em 
    diferentes locais, a AWS agrupa estas AZs em regiões. Por 
    esta razão, existem regiões em vários locais do mundo, 
    inclusive em São Paulo (sa-east-1).

    É importante ressaltar que nem todos os serviços da AWS estão 
    disponíveis em todas as regiões. Alguns serviços são lançados 
    em regiões de países com maior demanda e, para prova de 
    conceito, são incorporados gradativamente nas demais regiões.

    Ainda existem subdivisões desta infraestrutura, como zonas 
    locais, AWS Outposts e zonas de Wavelenght.

    Em resumo, segue a descrição de cada agrupamento:

        Cada Região é uma área geográfica separada. Exemplo:
        
            us-east-1 (North Virginia);
            
            sa-east-1 (São Paulo).
            
        As zonas de disponibilidade (AZs) são vários locais 
        isolados dentro de cada região. Exemplo:
        
            us-east-1a.
            
        As zonas locais fornecem a capacidade de colocar recursos, 
        como computação e armazenamento, em vários locais mais 
        próximos dos usuários finais.
        
            O código da zona local é o código da região pai, 
            seguido do identificador da zona local. Exemplo: 
            zona local us-west-2-lax-1 em Los Angeles e dentro 
            da região us-west-2.
        
        O AWS Outposts leva serviços, infraestrutura e modelos 
        operacionais nativos da AWS e, local do cliente. Este 
        serviço é conhecido como colocation. A AWS gerencia a 
        capacidade de computação como parte de uma região da AWS. 
        Ou seja, os recursos computacionais ficam no ambiente do 
        cliente (on-premises).
        
        As zonas do Wavelength permitem que os desenvolvedores 
        criem aplicações que oferecem baixíssimas latências para 
        dispositivos 5G e usuários finais. O Wavelength implanta 
        os serviços de armazenamento e computação padrão da AWS 
        até a borda das redes 5G de operadoras de telecomunicação.

    Vale ressaltar que as zonas locais e as Wavelength zones não 
    estão disponíveis em todas as regiões.

    Observação: é possível consultar a disponibilidade de regiões 
    no site: https://aws.amazon.com/pt/about-aws/global-infrastructure/, 
    já as zonas locais e Wavelengths podem ser consultadas na 
    página de documentação da AWS: https://docs.aws.amazon.com/

    Para decidir em qual região devemos alocar nossa nuvem privada,
    devemos considerar alguns critérios como:

        Proximidade: regiões mais próximas possuem menor latência, 
        ou seja, o tempo de acesso a um servidor mais próximo é 
        menor.
        
        Compliance: verifique as normas de armazenamento de dados 
        da empresa e se as normas de proteção de dados do país 
        (exemplo: LGPD) são compatíveis com as normas da região a 
        ser escolhida.
        
        Custo: os custos variam de acordo com região. Em alguns 
        casos, devido a uma maior infraestrutura, regiões mais 
        distantes têm custos menores.

Nuvem privada virtual (VPC):

    Uma nuvem privada virtual (Virtual Private Cloud — VPC) é 
    uma rede virtual dedicada à sua conta na AWS. Utilizando essa 
    rede, é possível provisionar recursos da AWS, como máquinas 
    virtuais, instâncias de banco de dados, entre outros. É uma 
    seção isolada logicamente de outros clientes da AWS. Ao 
    criarmos uma conta na AWS, já temos uma VPC padrão criada 
    para nós.

    Dentro da VPC, podemos criar sub-redes públicas ou privadas. 
    Uma VPC pode existir em apenas uma região, mas pode ter 
    sub-redes em outras AZs na mesma região.

    Para criar uma VPC, é importante lembrar que podemos escolher a 
    quantidade de sub-redes, além da quantidade de máquinas em cada 
    sub-rede. Para isso, vamos observar o padrão do IPv4, que 
    utiliza o sistema binário de 32 bits para definir um endereço 
    de IP (Internet Protocolo).

    Podemos usar uma parte do bloco de IP para definir os bits 
    usados para a rede e os bits usados para os equipamentos, 
    utilizando uma máscara de sub-rede. Para isso, podemos usar 
    uma notação conhecida como Class Inter-Domain Routing (CIDR), 
    que permite definir os bits usados para a rede e os bits 
    usados para os equipamentos.

    Considere o exemplo a seguir, onde definimos um bloco CIDR 
    IPv4 de 10.0.0.0/16. Neste caso, 16 bits são alocados para 
    a rede (10.0). Além disso, podemos criar diferentes sub-redes, 
    podendo alocar equipamentos de departamentos distintos, por 
    exemplo.

    Seguindo, temos 4 sub-redes. A sub-rede 1 está definida com o 
    endereço de rede 10.0.0. O último bloco de 8 bits do IP é 
    destinado para alocação de equipamentos, podendo chegar a 
    251 endereços IPs, sendo que alguns IPs são reservados:

        10.0.0.0 — Endereço de rede;
        
        10.0.0.1 — Comunicação Interna;
        
        10.0.0.2 — DNS;
        
        10.0.0.3 — Uso futuro;10.0.0.255 — Endereço de transmissão de 
        rede (broadcast)

    A AWS também suporta o conceito mais moderno de atribuição de 
    IPs (IPv6) que define 128 bits para endereçamento. Focaremos 
    apenas no IPv4.

    Vejamos um diagrama simples em que temos um servidor web e um 
    servidor de banco de dados, ambos implantados na nuvem.

    Neste exemplo, podemos observar um diagrama para a implantação 
    de uma VPC (10.0.0.0/16) na região de São Paulo (sa-east-1), 
    em uma única zona de disponibilidade (sa-east-1a). Existe uma 
    sub-rede pública (10.0.0.0/24) que contém um servidor web e 
    uma sub-rede privada que contém uma sub-rede privada com uma 
    instância de um banco de dados. Além disso, podemos observar 
    uma saída para a internet da VPC, o chamado Internet Gateway.

    Este é um cenário simples que pode ser implementado nas 
    empresas. Entretanto, existem outros serviços de rede que 
    podem ser incluídos com o intuito de garantir a disponibilidade 
    e o balanceamento de carga, ou até mesmo para proteger o 
    tráfego de entrada e saída da rede, por meio de um firewall.

    Vejamos agora o conceito de Security Group no próximo tópico.

Grupos de segurança (security groups):

    Um grupo de segurança (Security Group — SG) atua como um 
    firewall virtual que controla o tráfego de entrada e saída 
    para os dispositivos definidos em uma VPC, como máquinas 
    virtuais. No Security Group, podemos definir regras para 
    permitir ou negar tráfego com base em portas e protocolos 
    específicos.

    No Security Group, é possível definir quais portas são 
    liberadas tanto para a entrada de dados quanto para a saída 
    de dados. Por padrão, ao criar um grupo de segurança, todos 
    os acessos são limitados, fazendo com que seja necessário 
    configurar explicitamente as portas que precisamos liberar.

    Por exemplo, podemos liberar a porta 80 ou a porta 8080 para 
    acesso de qualquer IP em casos nos quais expomos um servidor 
    web para a internet. Assim, podemos “subir” um servidor web 
    para a nuvem da AWS, permitindo que seja acessível somente 
    pelas portas específicas. Veremos agora como gerenciar 
    máquinas virtuais na AWS.

Máquinas virtuais e tipos de armazanamento:

    O Elastic Compute Cloud (EC2) é um serviço de computação em 
    nuvem que permite criar instâncias de máquinas virtuais. 
    Neste serviço, podemos escolher diversas configurações de 
    máquinas e de sistemas operacionais, escolhendo imagens
    prontas da AWS (Amazon Machine Images — AMI). Também é 
    possível criarmos nossas próprias imagens para serem 
    reutilizadas diversas vezes.

    +-----------------------------------------------------------------------+-------------------------------------------------------------+
    | FAMÍLIA DE INSTÂNCIAS (AWS EC2)                                       | EXEMPLO DE USO                                              |
    +-----------------------------------------------------------------------+-------------------------------------------------------------+
    | Propósito Geral (General purpose)                                     | Sites web de baixo tráfego;                                 |
    | Ex: A1, T3, T3a, T2, M6g, M5                                          | Pequenas e médias bases de dados.                           |
    +-----------------------------------------------------------------------+-------------------------------------------------------------+
    | Otimizado para Processamento (Compute Optimized)                      | Sites web de alta performance;                              |
    | Ex: C5, C5n, C4, C7g                                                  | Processamento de vídeo.                                     |
    +-----------------------------------------------------------------------+-------------------------------------------------------------+
    | Otimizado para Memória (Memory Optimized)                             | Bancos de dados na memória                                  |
    | Ex: R5, R5n, X1e, X1, z1d                                             | (exemplo: Redis).                                           |
    +-----------------------------------------------------------------------+-------------------------------------------------------------+
    | Otimizado para Armazenamento (Storage Optimized)                      | Data warehousing;                                           |
    | Ex: I3, I3en, D2, H1                                                  | Aplicações que processam dados e logs.                      |
    +-----------------------------------------------------------------------+-------------------------------------------------------------+
    | Computação Acelorada (Accelerated computing)                          | Machine Learning;                                           |
    | Ex: P3, P2, Inf1, G4, G3, F1                                          | Visualizações 3D.                                           |
    +-----------------------------------------------------------------------+-------------------------------------------------------------+

    Existem instâncias para propósito geral, como pequenos 
    websites, até instâncias otimizadas para execução de trabalhos 
    de Machine Learning.

    Ao criar uma instância, os endereços IPs são atribuídos 
    dinamicamente, inclusive um IP público para acesso à internet 
    e outro para comunicação na sub-rede privada. No entanto, o 
    IP é renovado quando a instância é renovada. É possível 
    adquirir um serviço adicional para manter sempre o mesmo IP, 
    chamado de Elastic IP, podendo mover o IP entre as instâncias 
    existentes.

    Ao criar instâncias, definimos o espaço de armazenamento para 
    o sistema operacional e para discos externos. Estes espaços 
    são chamados de Elastic Block Storage.

Elastic Block Storage (EBS):

    O Elastic Block Storage é um tipo de HD (Hard Disk) virtual. 
    Por padrão, há um HD destinado para o sistema operacional, 
    como por exemplo, o disco C: em máquinas com o sistema 
    operacional Windows, com pelo menos 10 GB e no máximo 64TB. 
    Os dados armazenados neste volume (C:) são efêmeros e se 
    perdem toda vez que a instância é reiniciada. É possível 
    ainda criar outro volume do EBS que pode ser anexado a qualquer 
    instância, criando outra partição (exemplo: disco D:) e que 
    mantém os dados após reiniciar. Este volume adicional pode ser 
    mantido mesmo após a exclusão da instância e anexado 
    futuramente em outras instâncias.

    Por exemplo, podemos criar um volume EBS extra (D:) para 
    armazenar dados de um servidor web, enquanto o volume principal
    (C:) fica sendo utilizado apenas para armazenar dados do 
    sistema operacional.

    É possível escolher, além da capacidade de armazenamento do HD, 
    o tipo de HD, sendo Hard Disk Drives (HDD) ou Solid State Drives
    (SSD), e variações entre estas opções (exemplo: SSD NVMe).

    É possível ainda realizar backups dos HDs da AWS, criando uma 
    fotografia (snapshot) no tempo que pode eventualmente ser 
    restaurada quando necessário. Estes backups ficam armazenados 
    em um repositório de dados conhecido como S3.

    Portanto, podemos armazenar e alterar arquivos no volume EBS 
    sempre que necessário. Além do EBS, existem outros tipos de 
    armazenamento compatível apenas com sistemas Linux, que é o 
    Elastic File System (EFS), basicamente um drive de rede que 
    pode ser acessado simultaneamente por várias instâncias, e o 
    Amazon Simple Storage Service (S3).

Elastic File System (EFS):

    O Elastic File System (EFS) é um sistema de arquivos exclusivo 
    para instâncias EC2 com Linux. Ele funciona como um “drive” de
    rede, podendo ser acessado tanto pelas máquinas virtuais da AWS 
    quanto para máquinas on-premises do cliente. Algumas 
    características são:

        Usa o protocolo NFS;
        
        Auto-dimensionável (aumenta o tamanho conforme demanda);
        
        Permite editar arquivos em tempo real.

    Além do NFS, é possível armazenar diferentes tipos de arquivos, 
    sejam imagens, textos, entre outros, em outro serviço da AWS, 
    conhecido como Amazon S3.

Simple Storage Service (S3):

    O Amazon Simple Storage Service (S3) foi um dos primeiros 
    serviços lançados pela AWS e permite o armazenamento de 
    diferentes tipos de arquivos, como imagens, textos e demais 
    formatos. Ele utiliza o conceito de bucket, onde cada arquivo 
    armazenado é chamado de objeto. No S3, diferentemente do EBS, 
    não é possível alterar objetos. Ou seja, cada alteração 
    substitui completamente o objeto.

    Podemos armazenar, por exemplo, arquivos de aplicações, log, 
    vídeos, imagens e arquivos separados por vírgula (CSV) para 
    que sejam processados e depois incluídos em um banco de dados. 
    O custo de armazenamento no S3 é muito mais barato, possuindo 
    versões para uso recorrente, como o S3 Standard, e versões 
    específicas para armazenamento de longo prazo para uso em 
    auditorias, com o S3 Glacier. Podemos usar o S3 para a 
    construção de um data lake, servindo como um repositório 
    central de dados, para que depois sejam rodados algoritmos de 
    Machine Learning e Computação Distribuída.

    É possível ainda criar um site estático utilizando o serviço do
    S3. Para isso, basta subir um arquivo HTML em um bucket S3 e 
    expor o acesso ao bucket de forma pública pela internet, 
    configurando a política de acesso ao bucket.

    Após a criação de um bucket, é possível armazenar diferentes 
    tipos de arquivos diretamente ao bucket ou programaticamente, 
    por meio do SDK.

    Após a criação do bucket, se torna possível adicionar arquivos 
    ao mesmo, inclusive páginas estáticas HTML, para servir de site 
    institucional, por exemplo.

    Quando adicionamos qualquer objeto como arquivo, página html, 
    imagem, entre outros, é criada uma URL para acesso direto ao 
    objeto.

    A partir desta URL e fornecidas as devidas permissões de acesso 
    público (editada a política de segurança), podemos acessar de 
    qualquer lugar do mundo nosso site estático.

                    Banco de dados em Nuvem

A AWS oferece diversos tipos de bancos de dados na nuvem, desde 
instâncias de base de dados relacionais, com suporte ao MySQL, 
SQL Server e outros, até bases de dados NoSQL, como o DynamoDB, 
o AWS Neptune, e entre outros. Vamos explorar algumas das opções 
disponíveis.

Base de dados relacionais (RDS):

    Nas bases de dados relacionais, os dados são armazenados em 
    tabelas e usam apontamentos como chaves primárias e estrangeiras
    em um modelo de dados relacional, de maneira a minimizar 
    redundâncias, garantir que as operações sejam executadas 
    integralmente, a consistência dos dados, isolamento de 
    transações e durabilidade dos dados. Estas características são 
    conhecidas como ACID (Atomicidade, Consistência, Isolamento e 
    Durabilidade).

        Atomicidade: as operações em um banco de dados são 
        executadas completamente ou não são executadas.

        Consistência: a execução de uma transação deve levar de um 
        estado consistente a um outro estado consistente.

        Isolamento: cada transação é executada isoladamente da 
        outra, mesmo quando há concorrência.

        Durabilidade: após as transações, os dados são 
        persistentes, mesmo em caso de falhas.
    
    O Amazon Relational Database Services (RDS) oferece toda a 
    estrutura para armazenar bases de dados relacionais. Há 
    suporte para sistemas gerenciadores de bases de dados 
    tradicionais (SGBDs), como o MySQL, o MariaDB, o MS SQL Server,
    o Oracle e o PostgreSQL. Além disso, a AWS conta com um 
    SGDB customizado chamado Aurora, facilitando a escalabilidade 
    e disponibilidade.

    Ao criar uma instância de banco de dados, você não precisa se 
    preocupar em alocar uma máquina virtual e nem o sistema 
    operacional por trás do banco de dados pois a AWS já cria 
    automaticamente.

    Basta selecionar o tipo da instância, o nome do usuário 
    principal e senha, e a família de instância que irá armazenar a 
    base de dados, assim como o tamanho alocado para armazenamento. 
    Além das configurações básicas, precisamos definir uma VPC onde 
    a instância será instalada e um Security Group protegendo a 
    instância,  e, opcionalmente, o nome de uma base de dados. A 
    partir deste setup, é possível acessar a base de dados 
    remotamente ou direto pela AWS.

    O Editor de consultas do RDS permite acessar diretamente 
    somente as bases de dados do Amazon Aurora. Para consultar 
    bases de dados, como do MySQL, é possível a conexão remota 
    por meio do endereço da instância ou programaticamente, por 
    meio de funções ou códigos em Python, por exemplo.

    Ao clicar na instância, podemos obter detalhes de como acessar 
    remotamente.

Ingestão de dados:

    O processo de ingestão de dados, seja em uma base de dados, 
    seja em um repositório de objetos, como o S3, pode ser 
    efetuado de diferentes maneiras, sendo:

        ETL — Extract, Transform and Load;
        
        ELT — Extract, Load and Transform.

    O processo tradicional, conhecido como extração, transformação 
    e carga (Extract, Transform, Load — ETL), pode ser usado, por 
    exemplo, para ler um arquivo CSV, realizar uma transformação 
    simples, como exclusão de algumas colunas e seguir para uma 
    carga em uma base de dados relacional como o Amazon RDS ou até 
    mesmo em um DataWarehouse, como o Amazon Redshift.

    Além deste processo, podemos realizar o processo de extração, 
    carga e transformação (Extract, Transform, Load – ETL), quando 
    lidamos com grandes volumes de dados, para garantir a carga 
    dos dados brutos e depois transformar os dados de acordo com 
    os cenários de análise.

    Portanto, o volume dos dados impacta no processo de carga dos 
    dados em um banco de dados e até mesmo na escolha do banco de 
    dados a ser armazenado. O Amazon Redshift, por exemplo, é uma 
    base de dados colunar,  otimizada para armazenar grandes 
    volumes de dados e facilitando a consulta e agregação de dados, 
    pois usa paralelismo para ingestão e consulta.

    Em vários cenários de análises de dados, os dados podem ser 
    armazenados em um DataLake, composto por buckets S3 e bases de 
    dados, em que se mantém os dados brutos em um repositório S3. 
    Após um primeiro processamento, os dados podem ser filtrados, 
    limpos e padronizados, salvando-os em outro repositório, 
    chamado de dados confiáveis e, em seguida, podem ser 
    enriquecidos com novas colunas para projetos específicos, 
    conhecidos como dados curados. Esta arquitetura é conhecida 
    como “Arquitetura Medalhão”,  em que os dados brutos estão na 
    camada bronze, os dados confiáveis na camada prata e os dados 
    enriquecidos na cama ouro.

Consumo de dados:

    O consumo de dados por aplicações ou por analistas de dados 
    pode ser feito também por diversos serviços. O Amazon Athena 
    permite rodar consultas SQL diretamente em arquivos armazenados 
    em um bucket S3 ou a partir do Amazon Redshift. Para isso, 
    torna-se necessário catalogar as bases existentes em um data 
    lake usando o serviço do AWS Glue, que é um crawler que busca 
    em diferentes locais na nuvem da AWS. O crawler pode ser 
    disparado sob demanda ou programado para ser executado em um 
    horário específico.

    O AWS Glue permite identificar o schema da base de dados, 
    auto-inferindo as colunas e armazenando os metadados em um 
    catálogo para consulta posterior.

    Podemos agendar um crawler no AWS Glue para identificar e 
    catalogar diferentes fontes de dados, fazer e executar o 
    ETL para depois deixar os dados pesquisáveis por serviços, 
    como o AWS Athena ou o Amazon Quick Sight.

                    Serveless

Arquitetura Serveless:

    Uma arquitetura serverless é um modelo de computação em nuvem 
    na qual podemos disponibilizar aplicações completas sem nos 
    preocuparmos em gerenciar e configurar servidores.

    A infraestrutura e a escalabilidade são totalmente gerenciadas 
    pelo provedor de serviços de nuvem, como a AWS, permitindo que 
    os desenvolvedores foquem no problema de negócio e no código 
    que precisam desenvolver.

    Além de não se preocupar com a gestão de servidores, a forma 
    de cobrança é simplificada, não havendo cobrança por 
    servidores ociosos. O pagamento é feito sob demanda de acordo 
    com o que é solicitado.

    A arquitetura serverless permite a experimentação e testes 
    para projetos de pequeno porte, incluindo a disponibilização 
    de websites, o processamento assíncrono ou o processamento 
    de dados de streaming ou Internet das Coisas (IOT — Internet 
    of Things).

    Algumas vantagens são: 

        Redução de custos:  não há custo com ociosidade de 
        computadores.
        
        Alta disponibilidade e resiliência: a infraestrutura é 
        projetada para tolerar falhas e garantir alta 
        disponibilidade.
        
        Foco no negócio: o desenvolvedor por focar em resolver 
        os problemas de negócio ao invés de focar na gestão de 
        infraestrutura.
        
        Escalabilidade: as soluções ganham escalabilidade, sendo 
        capazes de atender a um número variável de usuários e 
        demandas.

Projeto real:

    A partir desse ponto, vamos aplicar uma solução real para um 
    sistema Serverless. Esse exemplo é totalmente aplicável em 
    sua vida profissional como arquiteto(a) de nuvem. Imagine que 
    você receberá dados de sensores que medem a temperatura de 
    hora em hora. Os dados chegarão em um bucket S3  e deverão 
    ser alimentados automaticamente em um banco de dados. Em 
    seguida, serão disponibilizados para consulta para os nossos 
    clientes.

    No passo 1 da solução, vamos simular a ingestão de dados e 
    receber um arquivo CSV de um fornecedor. O conteúdo do 
    arquivo deverá ser processado e armazenado em um bucket S3. 
    Ao receber os dados, uma função Lambda irá ser acionada 
    automaticamente para fazer a carga em um banco de dados, como 
    o DynamoDB.

    No passo 2 da solução, iremos preparar o consumo de dados, 
    disponibilizando uma API de consulta e utilizando o serviço 
    API Gateway, que permite criar APIs REST. Neste serviço, 
    disponibilizaremos um endereço de consulta dos dados por dia 
    aos nossos clientes.

    Para implantar esta solução, iremos abordar as características 
    dos serviços envolvidos, e como podemos acionar a automação 
    destes serviços.

            Ingestão e tranformação de dados na nuvem

Considerando a primeira parte de nossa solução completa de ingestão 
de dados, precisamos de um serviço da AWS que consiga processar um 
arquivo de entrada, filtrando os dados necessários, para depois 
gravar no banco de dados. Esta opção é o AWS Lambda. Inicialmente 
veremos alguns conceitos básicos e, em seguida, iremos aplicá-los 
ao nosso cenário.

AWS Lambda:

    O serviço AWS Lambda permite executar trechos de código em 
    resposta a eventos (event-driven), sem se preocupar em 
    gerenciar e configurar servidores (serverless).

    É possível executar códigos sob demanda em diferentes 
    linguagens de programação, como Python, nodejs, Java, go, 
    .net, entre outros.

    A cobrança é feita somente a partir de cada execução de código. 
    Portanto, paga-se de acordo com a quantidade de chamadas 
    realizadas, considerando o tempo de execução do código e a 
    quantidade de memória e CPU envolvidas.

    O desenvolvedor pode escrever seu código diretamente no console 
    da AWS ou realizar o upload de um arquivo ZIP, e o Lambda 
    automaticamente aloca os recursos necessários para executar o 
    código.

    O Lambda pode ser acionado por meio de eventos de outros 
    serviços, como a carga de arquivos em um bucket S3. Este 
    acionamento é chamado de gatilho (triggers)

    No entanto, o Lambda tem algumas restrições como:

        Alocação de memória: 128MB a 10 GB;

        Execuções simultâneas: 1000;

        Tempo máximo de execução: 15 minutos.

    Para soluções que exigem mais recursos, como por exemplo, se 
    o seu programa Python leva mais que 15 minutos para filtrar a 
    entrada, o Lambda não é adequado. Da mesma forma, se o arquivo 
    que você carregou, como um vídeo, possui mais de 10 GB para ser 
    processado, o Lambda também não irá suportar. Ou, se o seu 
    programa precisa manter estados entre execuções, isto é, 
    transferir valor de variáveis internas ou continuar o 
    processamento em outro programa Python alocado em um segundo 
    Lambda, o primeiro Lambda nem o segundo conseguirão suportar, 
    pois cada invocação ocorre em um ambiente efêmero.

    Um ambiente efêmero é um ambiente de execução que não mantém 
    estado entre execuções e é descartado após o uso. Isso 
    significa que, toda vez que uma função é invocada, ela pode ser 
    executada em um novo ambiente, sem acessar arquivos, variáveis 
    ou configurações das execuções anteriores.

    A solução será trocar o Lambda por um EC2, que permite 
    armazenamento persistente usando EBS  (Elastic Block Store) 
    ou discos locais.

    Tendo em vista essas limitações, vamos criar nossa primeira 
    função Lambda!

    Abra o AWS Academy e acesse o Learner Lab. Inicialmente, 
    busque por Lambda na guia de serviços.

    Lembre-se de selecionar a região “Norte da Virgínia” para a criação de suas funções, para que depois seja possível encontrá-las.

    Em seguida, clique no menu Lambda > Funções e selecione o botão 
    “Criar função”

    Defina o nome da função Lambda e o tempo de execução (runtime). 
    No tempo de execução, também é importante definirmos a linguagem
    de programação que utilizaremos ou o framework / engine 
    necessário para rodar nosso código. Neste caso, escolheremos o 
    Python.

    Expanda a opção de “Alterar a função de execução de execução 
    padrão” e selecione a opção “Usar uma função existente”. Como 
    estamos utilizando o ambiente de testes (Learner Lab), é 
    importante escolher a “LabRole” (role) para conseguir executar 
    a função. Finalmente, clique em “Criar função”.

    Ao criar a função, você visualizará um trecho de código na 
    linguagem que selecionou (neste caso, Python) e já poderá 
    testar a função.

    A seguir, iremos implantar a função Lambda e testá-la.

    Inicialmente iremos alterar o texto da função Lambda, de 
    acordo com o seguinte trecho de código:

        import json

        def lambda_handler(event, context):
            # TODO implement
            return {
                'statusCode': 200,
                'body': json.dumps('Ola Estudante AWS!')
            }

    O que esse código está fazendo? O AWS Lambda recebe um evento 
    de entrada (event) e um contexto (context) como entrada. O 
    “event” contém os dados que acionaram a função (como uma 
    requisição HTTP, um evento do S3, SNS, entre outros). O 
    “contexto” contém informações do ambiente de execução do 
    Lambda. A função retorna um dicionário com dois campos 
    principais:

        'statusCode': 200 → Indica que a requisição foi bem-sucedida.
        
        'body': json.dumps('Ola FIAP ON!') → Retorna a string "Ola 
        Estudante AWS!" no formato JSON.

    Isso significa que, ao ser chamada via API Gateway, por 
    exemplo, ela responderá com um código HTTP 200 e o corpo da 
    resposta conterá a string "Ola FIAP ON!" em JSON.

    Toda alteração em uma função Lambda requer que a função seja 
    reimplantada (deploy). Portanto, selecione a opção “Deploy” e, 
    em seguida, clique no botão “Test”.

    Você irá nomear um evento de teste, como “TesteOlaAlunos”. É 
    possível ainda customizar um arquivo JSON de entrada para o 
    evento. No entanto, mantenha as opções padrão.

        Transformação de dados com funções lambda

Iremos implementar a primeira etapa da nossa solução completa. Para 
tanto, iremos criar funções Lambda que serão acionadas 
automaticamente.

O banco de dados DynamoDB foi escolhido por ser uma base de dados 
serverless, ou seja, está alinhado com os requisitos da nossa 
solução de não nos preocuparmos com as instalações. No entanto, ele 
não suporta ingestão de arquivos por CSV, e sim, por meio de 
arquivos JSON. Portanto, teremos que transformar os dados 
inicialmente estruturados do CSV no formato JSON.

Podemos observar uma sequência de transformações sofridas por um 
arquivo de entrada no formato CSV. O arquivo é carregado 
inicialmente em um bucket de entrada do S3.

Em seguida, uma função Lambda denominada “ProcessarArquivosCSV” 
irá processar o arquivo CSV e transformá-lo em um formato JSON 
para que possa alimentar nosso banco de dados DynamoDB.

Finalmente, uma outra função Lambda denominada 
“ProcessarArquivosJSON” irá ler o arquivo JSON e inserir os dados 
no banco de dados DynamoDB. O processo inteiro será acionado 
automaticamente por meio de gatilhos. Vejamos a seguir como 
configurar esses gatilhos.

    Disparo automático de funções lambda (triggers)

A função Lambda pode ser executada automaticamente quando ocorre algum evento na AWS, como, por exemplo, a carga de dados em um bucket S3. Essa execução é chamada de “gatilho” ou trigger.

Para simular este processamento automático, iremos criar dois buckets S3 com o padrão:

    fiapon-<suasiniciais>-arquivos-entrada
    
    fiapon-<suasiniciais>-arquivos-processados

Altere o bucket de origem e destino para suas iniciais. Por 
exemplo, considerando que meu nome é Fernando Timóteo Fernandes, 
e também o padrão sugerido “fiapon-<suasiniciais>-arquivos-entrada”,
temos o seguinte bucket: “fiapon-ftf-arquivos-entrada”.

Após a criação dos buckets, você deverá ter os seguintes buckets, 
lembrando que o nome dos buckets deverá refletir suas iniciais.

Agora, vamos agora criar uma função Lambda chamada 
“ProcessarArquivosCSV” para ler o arquivo a ser enviado ao bucket 
de entrada. Adapte o seguinte código, alterando o nome dos buckets 
de acordo com suas iniciais:

    import boto3
    import csv
    import json
    import os
    from datetime import datetime

    # Buckets
    bucket_origem = 'fiapon-<suasiniciais>-arquivos-entrada'
    bucket_destino = 'fiapon-<suasiniciais>-arquivos-processados'

    # Função para processar um único arquivo do bucket de origem e retorna uma lista
    def processar_arquivo(bucket_origem, nome_arquivo, s3_client):
        resultados = []
        try:
            print(f"Processando arquivo: {nome_arquivo}")

            # Ler o arquivo do S3
            arquivo_obj = s3_client.get_object(Bucket=bucket_origem, Key=nome_arquivo)
            arquivo_conteudo = arquivo_obj['Body'].read().decode('utf-8').splitlines()

            # Processar o CSV
            leitor_csv = csv.DictReader(arquivo_conteudo)

            for linha in leitor_csv:
                try:
                    temperatura = int(float(linha.get("temperatura", 0)))
                except ValueError:
                    temperatura = 0

                resultados.append({
                    "id_estacao": linha.get("id_estacao", ""),
                    "nome_arquivo": nome_arquivo,
                    "data": linha.get("data", ""),
                    "latitude": linha.get("latitude", ""),
                    "longitude": linha.get("longitude", ""),
                    "temperatura": temperatura
                })

            # Excluir o arquivo de origem após o processamento
            s3_client.delete_object(Bucket=bucket_origem, Key=nome_arquivo)
            print(f"Arquivo {nome_arquivo} excluído do bucket de origem.")

        except Exception as e:
            print(f"Erro ao processar o arquivo {nome_arquivo}: {e}")
            resultados.append({"nome_arquivo": nome_arquivo, "erro": str(e)})

        return resultados

    # Função Lambda principal
    def lambda_handler(event, context):
        # Inicializar o cliente S3
        s3 = boto3.client('s3')

        try:
            # Recuperar o nome do arquivo do evento
            registro = event['Records'][0]
            nome_arquivo = registro['s3']['object']['key']

            # Processar o arquivo
            resultados = processar_arquivo(bucket_origem, nome_arquivo, s3)

            # Gerar o JSON com os resultados
            if resultados:
                timestamp = datetime.utcnow().strftime('%Y_%m_%d_%H_%M_%S')

                nome_arquivo_base = os.path.splitext(nome_arquivo.split('/')[-1])[0]
                nome_arquivo_json = f"{nome_arquivo_base}_processado_{timestamp}.json"

                # Salvar o JSON no bucket de destino
                json_resultados = json.dumps(resultados, indent=4)
                s3.put_object(
                    Bucket=bucket_destino,
                    Key=nome_arquivo_json,
                    Body=json_resultados,
                    ContentType='application/json'
                )
                print(f"Arquivo JSON {nome_arquivo_json} gerado no bucket {bucket_destino}")

            # Retornar JSON de sucesso
            return {
                "statusCode": 200,
                "body": {
                    "mensagem": "Arquivo processado com sucesso!",
                    "arquivo_processado": nome_arquivo,
                    "resultado_arquivo": nome_arquivo_json
                }
            }

        except KeyError as e:
            print(f"Erro: parâmetro ausente - {e}")
            return {
                "statusCode": 400,
                "body": {
                    "mensagem": "Erro: Nome do arquivo ausente no evento."
                }
            }
        except Exception as e:
            print(f"Erro geral ao processar o arquivo: {e}")
            return {
                "statusCode": 500,
                "body": {
                    "error": str(e)
                }
            }

Explicando sucintamente o que esse código faz, ele implementa uma 
função AWS Lambda para processar arquivos CSV armazenados no 
Amazon S3. Isto é, ele automatiza a leitura, transformação e 
movimentação de arquivos entre dois buckets S3, além de gerar um 
relatório JSON com os dados processados. Seu fluxo possui cinco 
etapas:

    Evento de Upload no S3:
    
        A função é acionada automaticamente sempre que um arquivo 
        é enviado ao bucket de entrada (fiapon-<suasiniciais>-
        arquivos-entrada).
        
        O evento fornece o nome do arquivo recém-carregado.
        
    Processamento do Arquivo CSV:
    
        A função lê o arquivo CSV do S3, decodificando seu 
        conteúdo.
        
        Usa a biblioteca csv.DictReader para transformar as 
        linhas do CSV em um formato dicionário.
        
        Converte a temperatura para um número inteiro, garantindo 
        que valores inválidos não causem falhas.
        
        Extrai dados importantes: ID da estação, data, latitude, 
        longitude e temperatura.
        
    Exclusão do Arquivo Original:
    
        Após o processamento, o arquivo é excluído do bucket de 
        origem, garantindo que ele não seja processado novamente.
        
        Geração de JSON com os Resultados:
        
            Um arquivo JSON contendo os dados processados é 
            criado com um timestamp UTC no nome.
            
            Esse JSON é salvo no bucket de saída (fiapon-
            <suasiniciais>-arquivos-processados).
            
        Retorno da Função:
        
            Se tudo der certo, a função retorna um status 200, 
            indicando sucesso.
            
            Caso ocorra um erro (como um arquivo corrompido ou 
            erro de permissão no S3), um código de erro 
            apropriado (400 ou 500) é retornado, junto com a 
            descrição do problema.

        cat > lambda_function.py <<EOF
        import boto3
        import csv
        import json
        import os
        from datetime import datetime

        bucket_origem = '$BUCKET_IN'
        bucket_destino = '$BUCKET_OUT'

        def processar_arquivo(bucket_origem, nome_arquivo, s3_client):
            resultados = []

            try:
                print(f"Processando arquivo: {nome_arquivo}")

                arquivo_obj = s3_client.get_object(
                    Bucket=bucket_origem,
                    Key=nome_arquivo
                )

                arquivo_conteudo = (
                    arquivo_obj['Body']
                    .read()
                    .decode('utf-8')
                    .splitlines()
                )

                leitor_csv = csv.DictReader(arquivo_conteudo)

                for linha in leitor_csv:
                    try:
                        temperatura = int(
                            float(linha.get("temperatura", 0))
                        )
                    except ValueError:
                        temperatura = 0

                    resultados.append({
                        "id_estacao": linha.get("id_estacao", ""),
                        "nome_arquivo": nome_arquivo,
                        "data": linha.get("data", ""),
                        "latitude": linha.get("latitude", ""),
                        "longitude": linha.get("longitude", ""),
                        "temperatura": temperatura
                    })

                s3_client.delete_object(
                    Bucket=bucket_origem,
                    Key=nome_arquivo
                )

                print(
                    f"Arquivo {nome_arquivo} excluído "
                    "do bucket de origem."
                )

            except Exception as e:
                print(
                    f"Erro ao processar o arquivo "
                    f"{nome_arquivo}: {e}"
                )

                resultados.append({
                    "nome_arquivo": nome_arquivo,
                    "erro": str(e)
                })

            return resultados


        def lambda_handler(event, context):
            s3 = boto3.client('s3')

            try:
                registro = event['Records'][0]
                nome_arquivo = registro['s3']['object']['key']

                resultados = processar_arquivo(
                    bucket_origem,
                    nome_arquivo,
                    s3
                )

                if resultados:
                    timestamp = datetime.utcnow().strftime(
                        '%Y_%m_%d_%H_%M_%S'
                    )

                    nome_arquivo_base = os.path.splitext(
                        nome_arquivo.split('/')[-1]
                    )[0]

                    nome_arquivo_json = (
                        f"{nome_arquivo_base}_"
                        f"processado_{timestamp}.json"
                    )

                    json_resultados = json.dumps(
                        resultados,
                        indent=4
                    )

                    s3.put_object(
                        Bucket=bucket_destino,
                        Key=nome_arquivo_json,
                        Body=json_resultados,
                        ContentType='application/json'
                    )

                    print(
                        f"Arquivo JSON {nome_arquivo_json} "
                        f"gerado no bucket {bucket_destino}"
                    )

                return {
                    "statusCode": 200,
                    "body": {
                        "mensagem":
                            "Arquivo processado com sucesso!",
                        "arquivo_processado":
                            nome_arquivo,
                        "resultado_arquivo":
                            nome_arquivo_json
                    }
                }

            except KeyError as e:
                print(f"Erro: parâmetro ausente - {e}")

                return {
                    "statusCode": 400,
                    "body": {
                        "mensagem":
                            "Erro: Nome do arquivo ausente no evento."
                    }
                }

            except Exception as e:
                print(
                    f"Erro geral ao processar o arquivo: {e}"
                )

                return {
                    "statusCode": 500,
                    "body": {
                        "error": str(e)
                    }
                }
        EOF

        Ingestão de dados com funções lambda

Nesta etapa, vamos criar uma outra função Lambda que fará a 
leitura dos arquivos JSON gerados e gravará em uma tabela do 
DynamoDB.

Para isso, crie a função “ProcessarArquivosJSON” com o seguinte 
conteúdo. Note que a parte em destaque (bucket_json = 
'fiapon-<suasiniciais>-arquivos-processados') é para que você 
altere o nome do bucket com suas iniciais.

    import boto3
    import json
    import uuid
    import logging

    # Inicialização dos clientes AWS
    s3_client = boto3.client('s3')
    dynamodb = boto3.resource('dynamodb')
    table = dynamodb.Table('temperaturas')

    logger = logging.getLogger()
    logger.setLevel(logging.INFO)

    bucket_json = 'fiapon-<suasiniciais>-arquivos-processados'


    def lambda_handler(event, context):
        try:
            # Obtendo informações do evento do S3
            file_key = event['Records'][0]['s3']['object']['key']

            logger.info(f"Processando arquivo: {file_key} do bucket: {bucket_json}")

            # Baixar o arquivo JSON do bucket
            response = s3_client.get_object(Bucket=bucket_json, Key=file_key)
            file_content = response['Body'].read().decode('utf-8')

            # Parse do conteúdo do arquivo JSON
            data = json.loads(file_content)

            # Inserir cada item no DynamoDB
            for item in data:
                table.put_item(
                    Item={
                        'id': str(uuid.uuid4()),  # Gerar um UUID único
                        'data': item['data'],
                        'id_estacao': item['id_estacao'],
                        'nome_arquivo': item['nome_arquivo'],
                        'latitude': item['latitude'],
                        'longitude': item['longitude'],
                        'temperatura': item['temperatura']
                    }
                )
                logger.info(f"Registro inserido no DynamoDB: {item}")

            # Excluindo o arquivo do bucket após o processamento
            s3_client.delete_object(Bucket=bucket_json, Key=file_key)
            logger.info(f"Arquivo {file_key} excluído do bucket {bucket_json}")

            return {
                'statusCode': 200,
                'body': json.dumps(f"Arquivo {file_key} processado com sucesso.")
            }

        except Exception as e:
            logger.error(f"Erro ao processar arquivo: {str(e)}")
            return {
                'statusCode': 500,
                'body': json.dumps(f"Erro ao processar arquivo: {str(e)}")
            }

Explicando rapidamente o objetivo do código anterior, ele 
implementa uma função AWS Lambda que processa arquivos JSON 
armazenados no Amazon S3 e insere seus dados em uma tabela do 
DynamoDB. Ele é acionado automaticamente sempre que um novo 
arquivo JSON é carregado no bucket S3 definido.

Primeiramente, a função obtém o nome do arquivo a partir do 
evento de trigger do S3. Em seguida, faz o download do JSON, 
lê seu conteúdo e converte para um formato Python utilizando 
json.loads(). Assim, cada registro do JSON é inserido no DynamoDB, 
onde recebe um UUID único como identificador.

Após a inserção bem-sucedida dos dados na tabela, o arquivo JSON 
original é excluído do bucket S3 para evitar reprocessamento. Caso 
ocorra algum erro, a função registra a falha nos logs do CloudWatch
e retorna um código de erro HTTP 500.

Dando sequência com o código anterior, preparamos a função Lambda 
para processar o arquivo JSON e inserir os registros no DynamoDB. 
No entanto, ainda não iremos executá-lo, pois iremos acioná-lo 
automaticamente por meio de uma API.

Finalizamos a ingestão de dados serverless utilizando as funções

                Consumo de dados na nuvem

Neste momento, iremos implementar a segunda parte de nossa 
solução serverless, onde consumiremos os dados do DynamoDB 
por meio de uma API, como pode ser vista na arquitetura da 
solução, destacada em laranja na figura a seguir.

Uma API (Application Programming Interface) permite a troca de 
informações entre sistemas distintos, padronizando o formato do 
arquivo a ser trocado.

Portanto, é possível consumir dados produzidos por sistemas com 
tecnologias distintas, desde que tais tecnologias estejam aptas 
a consumir os dados no formato especificado.

É possível utilizar diferentes tipos de formatos padronizados, 
como XML e JSON. 

A AWS oferece a possibilidade de criação de APIs REST na nuvem, 
com o serviço denominado API Gateway. Primeiro vamos entender os 
conceitos básicos de uma API para então criarmos nossa API de 
consumo na AWS.

                    API Gateway

A AWS permite criar diferentes tipos de APIs, como:

    API WebSocket

    API HTTP

    API REST

Uma API WebSocket permite estabelecer um canal aberto para a 
troca de mensagens entre um cliente e um servidor, como a criação 
de um chat.

Uma API REST (Representational State Transfer) é um estilo 
arquitetural para construir serviços web que permitem a 
comunicação entre sistemas, geralmente usando o protocolo HTTP. 
Em uma API REST, cada operação é independente e os dados enviados 
não são reutilizados, o que comumente é descrito como o não 
mantenimento de estado entre as operações.

A API HTTP e a API REST são ambas RESTful, ou seja, não mantêm 
estado entre as operações. Elas diferem em relação às questões 
de custos e recursos de implementação.

Na API HTTP é possível utilizar a autenticação mais simples com 
o uso de JWT (JSON Web Token). O JWT é uma forma de autenticação 
que permite que um servidor verifique a identidade de um usuário 
sem precisar armazenar informações sobre ele.

A API REST não conta com autenticação por meio de JWT, mas conta 
com diversos outros recursos, como a criação de chaves de API e 
integração à serviços de autenticação, como o Amazon Cognito. 
Também é possível estabelecer limites de chamadas por clientes, 
caching e validação de requisição antes de executar uma integração 
com o API REST.

A API HTTP se destaca por ter um tempo menor de resposta desde a 
requisição até a resposta a um recurso da API (latência) a um 
custo reduzido em comparação com a API REST. Cada recurso é 
identificado por uma URI (Uniform Resource Identifier) e por uma 
rota que acessa um recurso. O endereço base da API, seguido do 
nome de um recurso normalmente, é chamado de endpoint. Por exemplo: 
https://api.exemplo.com/temperaturas. Nesta URL, poderíamos 
consultar todas as temperaturas armazenadas em um banco de dados, 
a partir da integração com uma função Lambda.

É importante ressaltar que, ao criar uma API HTTP, é possível 
criar somente endpoints públicos. Já nas API REST, é possível 
criar tanto endpoints públicos como privados acessíveis somente 
dentro da VPC.

Métodos HTTP:

    As APIs RESTful seguem um conjunto de princípios e convenções para permitir operações de criação, leitura, atualização e exclusão de itens, por exemplo: Create, Read, Update e Delete — CRUD.

    Os métodos HTTP são utilizados para realizar operações em recursos:

        Método GET: recuperar um recurso (exemplo: listar 
        registros de temperaturas).

        Método POST: criar um novo recurso (exemplo: adicionar 
        um novo registro).

        Método PUT: atualizar completamente um recurso existente 
        (exemplo: editar um registro).

        Método PATCH: atualizar parcialmente um recurso existente.

        Método DELETE: remover um recurso (exemplo: excluir um 
        registro).

    Cada requisição HTTP pode retornar um dos seguintes status:

        1XX – Informativo

        2XX – Sucesso, por exemplo, HTTP 200 – OK; 
        201 – Criação de um registro; 204 – Exclusão bem sucedida.

        3XX – Redirecionamento para outra URL, por exemplo, 
        Erro: 301 - Recurso Movido Permanentemente.

        4XX – Erros na requisição do cliente, por exemplo, 
        Erro: 404 – página não encontrada.

        5XX – Erros do Servidor, por exemplo: 
        Erro 500 – Internal Server Error.

    O ideal é recebermos o retorno com o status 200, significando 
    que a requisição foi bem-sucedida. 

    Agora que sabemos as características de uma API, iremos criar 
    uma API que permite realizar consultas em um banco de dados 
    DynamoDB.

Consumo da API:

    A URL irá apontar para nossa API, tanto para realizar 
    consultas de todas as temperaturas, ou por uma data 
    específica. Para isso, a API acionará uma função Lambda 
    que irá ler os dados de temperaturas do DynamoDB.

    Iremos utilizar uma única API para duas operações, uma de 
    consulta geral e outra de consulta por data. A API acionará 
    uma função Lambda para ler os dados do DynamoDB. Portanto, 
    crie uma função Lambda com o nome “api-http-dynamodb” para 
    processar as chamadas da API e consultar a tabela 
    “temperaturas” do DynamoDB.

        import json
        import boto3
        import uuid
        from datetime import datetime
        from boto3.dynamodb.conditions import Attr

        client = boto3.client('dynamodb')
        dynamodb = boto3.resource("dynamodb")
        table = dynamodb.Table('temperaturas')
        tableName = 'temperaturas'

        def lambda_handler(event, context):
            print(event)
            body = {}
            statusCode = 200
            headers = {
                "Content-Type": "application/json"
            }

            try:
                if event['routeKey'] == "GET /temperaturas":
                    body = table.scan()
                    body = body["Items"]
                    print("Medicoes----")
                    print(body)
                    body = sorted(body, key=lambda x: x['data'])
                    responseBody = []
                    for items in body:
                        responseItems = {
                            'id_estacao': int(items['id_estacao']),
                            'id': items['id'],
                            'data': items['data'],
                            'temperatura': int(items['temperatura']),
                            'latitude': float(items['latitude']),
                            'longitude': float(items['longitude']),
                            'nome_arquivo': items['nome_arquivo']
                        }
                        responseBody.append(responseItems)
                    body = responseBody

                elif event['routeKey'] == "GET /temperaturas/data/{data}":
                    data_param = event['pathParameters']['data']
                    try:
                        # Convert data_param to date
                        date_filter = datetime.strptime(data_param, "%Y-%m-%d").date()

                        # Filter by date ignoring timestamp
                        response = table.scan(
                            FilterExpression=Attr('data').begins_with(str(date_filter))
                        )

                        responseBody = []

                        for items in response["Items"]:
                            responseItems = {
                                'id_estacao': int(items['id_estacao']),
                                'id': items['id'],
                                'temperatura': int(items['temperatura']),
                                'latitude': float(items['latitude']),
                                'longitude': float(items['longitude']),
                                'nome_arquivo': items['nome_arquivo'],
                                'data': items['data']
                            }
                            responseBody.append(responseItems)

                        body = sorted(responseBody, key=lambda x: x['data'])

                        print("Dados filtrados por data----")
                        print(body)

                    except ValueError:
                        statusCode = 400
                        body = f"Data invalida: {data_param}. Formato esperado: YYYY-MM-DD"

            except KeyError:
                statusCode = 400
                body = 'Rota nao suportada: ' + event['routeKey']
            body = json.dumps(body)
            res = {
                "statusCode": statusCode,
                "headers": {
                    "Content-Type": "application/json"
                },
                "body": body
            }
            return res

    expõe uma API para consultar medições de temperatura 
    armazenadas no Amazon DynamoDB. Ele responde a requisições 
    GET, permitindo recuperar todas as medições ou filtrar por uma 
    data específica.

    Quando a requisição "GET /temperaturas" é recebida, a função 
    escaneia a tabela "temperaturas" no DynamoDB, ordena os 
    registros pela data e retorna um JSON contendo informações 
    como ID da estação, data, temperatura, latitude  e longitude.

    Se a requisição seguir o formato "GET /temperaturas/data/{data}",

    formato de data (YYYY-MM-DD) e busca registros que começam com 
    essa data. Os resultados são organizados e retornados em JSON.

    Caso a rota solicitada não seja suportada ou a data esteja em 
    formato inválido, a função responde com um código de erro HTTP 
    400 e uma mensagem apropriada. Toda a comunicação é estruturada
    no formato JSON para facilitar a integração com serviços 
    externos.

        Crie o arquivo:

            cat > processar_json.py <<EOF
            import boto3
            import json
            import uuid
            import logging

            # Clientes AWS
            s3_client = boto3.client('s3')
            dynamodb = boto3.resource('dynamodb')

            # Tabela DynamoDB
            table = dynamodb.Table('temperaturas')

            # Logs
            logger = logging.getLogger()
            logger.setLevel(logging.INFO)

            # Bucket que contém os JSONs
            bucket_json = '$BUCKET_OUT'


            def lambda_handler(event, context):
                try:
                    # Pega o nome do arquivo enviado ao S3
                    file_key = event['Records'][0]['s3']['object']['key']

                    logger.info(
                        f"Processando arquivo: {file_key} "
                        f"do bucket: {bucket_json}"
                    )

                    # Baixar JSON
                    response = s3_client.get_object(
                        Bucket=bucket_json,
                        Key=file_key
                    )

                    file_content = (
                        response['Body']
                        .read()
                        .decode('utf-8')
                    )

                    # Converter JSON para Python
                    data = json.loads(file_content)

                    # Inserir cada registro no DynamoDB
                    for item in data:

                        table.put_item(
                            Item={
                                'id': str(uuid.uuid4()),
                                'data': item['data'],
                                'id_estacao': item['id_estacao'],
                                'nome_arquivo': item['nome_arquivo'],
                                'latitude': item['latitude'],
                                'longitude': item['longitude'],
                                'temperatura': item['temperatura']
                            }
                        )

                        logger.info(
                            f"Registro inserido no DynamoDB: {item}"
                        )

                    # Excluir o JSON após processar
                    s3_client.delete_object(
                        Bucket=bucket_json,
                        Key=file_key
                    )

                    logger.info(
                        f"Arquivo {file_key} excluído "
                        f"do bucket {bucket_json}"
                    )

                    return {
                        'statusCode': 200,
                        'body': json.dumps(
                            f"Arquivo {file_key} processado com sucesso."
                        )
                    }

                except Exception as e:

                    logger.error(
                        f"Erro ao processar arquivo: {str(e)}"
                    )

                    return {
                        'statusCode': 500,
                        'body': json.dumps(
                            f"Erro ao processar arquivo: {str(e)}"
                        )
                    }
            EOF

            AWS em tempo certo: Processos assíncronos, 
            alertas e monitoramento inteligente

A AWS permite processar trabalhos de forma assíncrona usando 
serviços de mensageria como o Simple Queue Service (SQS), o 
Simple Notification Service (SNS) e os códigos serverless com
Lambda.

Utilizando os serviços de mensageria, é possível:

    Criar um fluxo assíncrono de mensagens;
    
    Garantir a entrega de mensagens pelo menos uma vez;
    
    Integrar aplicações em um sistema distribuído;
    
    Comunicar aos assinantes sobre novas mensagens.

Além de criar um fluxo assíncrono, é importante monitorar a 
execução de serviços no ambiente da AWS. Para isso, veremos 
como trabalhar com o CloudWatch, que monitora os recursos da 
AWS além de permitir criar alertas.

Projeto real:

    Temos o seguinte cenário: imagine que você atua em um 
    e-commerce e precisa processar pedidos de forma assíncrona, 
    sinalizando o recebimento dos pedidos e confirmando o 
    pagamento.

    A seguir, podemos visualizar o diagrama da solução assíncrona 
    para o processamento de imagens na AWS. Note os serviços 
    envolvidos e as “caixinhas” protegendo esses serviços.

    Para este cenário, precisamos criar uma esteira de 
    processamento assíncrono que irá receber pedidos confirmados 
    de clientes, e que utilizaremos os serviços de mensageria da 
    AWS para comunicação e processamento dos pedidos.

            Processamento assíncrono e mensageria

Antes de iniciarmos com nosso projeto, iremos abordar os 
conceitos básicos de mensageria na AWS e suas principais 
características.

Simple Queue Services (SQS):

    O Amazon Simple Queue Service (SQS) foi um dos primeiros 
    serviços lançados pela AWS. Surgiu em 2006 como parte dos 
    primeiros serviços de computação em nuvem da empresa.

    Ele foi projetado para resolver problemas de comunicação 
    assíncrona entre sistemas distribuídos, permitindo o 
    desacoplamento entre componentes de software.

    O SQS trabalha com o conceito de filas, em que a primeira 
    mensagem que chega é a primeira a ser consumida.

    As mensagens vão se acumulando em uma fila e podem ser 
    consumidas por outras aplicações. Vale destacar que as 
    aplicações consumidoras precisam consultar ativamente a 
    fila para verificar a existência de mensagens, e, assim, 
    consumi-las. Esse processo é conhecido como mecanismo pull, 
    em que os consumidores acessam constantemente uma fila, leem 
    a mensagem e, em seguida, a removem da fila.

    As mensagens no SQS podem conter até 256 KB de dados (incluindo texto e o formato JSON). Elas são mantidas temporariamente na fila até serem processadas por um consumidor.

    O SQS pode trabalhar com os seguintes tipos de fila:

        Fila padrão (Standard Queue): provê alta escalabilidade, 
        mas sem garantia de ordem exata das mensagens.
        
        Fila FIFO: mantém a ordem exata das mensagens e garante 
        que cada mensagem seja processada apenas uma vez. Ideal 
        para processamento ordenado.

    Na fila padrão, há uma taxa de transferência muito alta, 
    porém, não há uma garantia de ordenação. Em contrapartida, 
    na fila do tipo FIFO, há a garantia de ordenação, porém, 
    com uma taxa de transferência ligeiramente inferior.

    No tipo de fila FIFO, a ordenação é realizada utilizando o 
    atributo “MessageGroupId” e de duplicação, por meio do 
    atributo “MessageDeduplicationId” definido pelo próprio 
    usuário. Caso uma mensagem com o mesmo “MessageDeduplicationId” 
    seja enviada dentro de um período de 5 minutos, ela será 
    ignorada.

    Uma vez que uma mensagem é recebida por um consumidor, ela 
    entra em um período de timeout (tempo de visibilidade), 
    impedindo que outros consumidores a processem novamente até 
    que o tempo expire. Se a mensagem não for confirmada como 
    processada, ela retorna à fila para ser processada novamente.

O SQS pode armazenar mensagens que falharam em uma fila chamada 
de Dead Letter Queue (DLQ).

É possível configurar a entrega de mensagens das seguintes formas:

    Sondagem curta (Short Polling): retorna mensagens da fila 
    imediatamente, mesmo que a fila esteja vazia. Pode gerar 
    requisições desnecessárias.
    
    Sondagem longa (Long Polling): aguarda até 20 segundos antes 
    de retornar uma resposta, reduzindo custos de requisição e 
    melhorando a eficiência das entregas.

O SQS também suporta processamento em lote (batch processing) com 
o envio e a exclusão de até 10 mensagens por vez.

Antes de iniciarmos nosso projeto, vamos abordar os conceitos 
básicos de outro serviço de mensageria como o Simple Notification 
Service (SNS).

Simple Notification Service:

    O Amazon SNS é um serviço de mensageria do tipo “pub/sub” 
    (publicação/assinatura) gerenciado pela AWS, projetado para 
    entrega assíncrona de mensagens.

    O SNS permite que publicadores (publishers) enviem mensagens 
    para um tópico SNS e os assinantes (subscribers) se inscrevam 
    em tópicos específicos para serem notificados automaticamente.

    Um tópico no SNS é um canal lógico de comunicação que permite 
    o envio de mensagens para múltiplos assinantes (subscribers). 
    Ele atua como um hub, onde os publicadores enviam mensagens e 
    os assinantes recebem essas mensagens automaticamente.

    O envio de mensagens utiliza o mecanismo de push, em que os 
    assinantes recebem passivamente as mensagens à medida em que 
    são publicadas nos tópicos.

    Esse mecanismo é bastante utilizado em nosso dia a dia, como 
    no caso de recebimento de notificações em um smartphone como, 
    por exemplo, as mensagens de texto por SMS.

    O SNS suporta diversos protocolos e consegue enviar mensagens 
    para serviços da AWS ou serviços externos à AWS, como e-mail 
    e SMS.

    A partir da publicação, a mesma mensagem pode ser enviada 
    para diversos assinantes, como e-mails cadastrados, envio 
    de mensagens SMS, filas do SQS e até mesmo funções Lambda.

    Quando uma mensagem é entregue, não há como buscá-la 
    novamente e o SNS não oferece recursos de armazenamento 
    de mensagens.

SNS vs SQS:

    Diferentemente do SQS, que utiliza o mecanismo de sondagem 
    (pull) em que os clientes precisam consultar ativamente uma 
    fila, o SNS envia as mensagens por seu mecanismo de push. Ou 
    seja, o SNS consegue enviar uma mensagem para vários assinantes 
    ao mesmo tempo, o que não é possível com o SQS. Entretanto, o 
    SNS não oferece recursos de reprocessamento de mensagens, como 
    o envio para uma fila morta (Dead letter Queue) como acontece 
    no SQS.

    Vejamos um resumo das características do SNS em comparação com 
    o SQS no quadro a seguir:

        x==============x========================x=======================x
        |   Recurso    |          SNS           |          SQS          |
        |              | (Publicador/Assinante) | (Produtor/Consumidor) |
        x==============x========================x=======================x
        |  Produtor/   | Publicar/Assinar       | Enviar/Receber        |
        |  consumidor  |                        |                       |
        x--------------x------------------------x-----------------------x
        |  Mecanismo   | Push (passivo)         | Sondagem (ativa)      |
        |  de entrega  |                        |                       |
        x--------------x------------------------x-----------------------x
        | Modelo de    | Muitos para muitos     | Um para um            |
        | distribuição |                        |                       |
        x--------------x------------------------x-----------------------x
        | Persistência | Não                    | Sim                   |
        | de mensagens |                        |                       |
        x--------------x------------------------x-----------------------x

    Conforme observado no quadro “SNS x SQS”, o SNS é um serviço 
    do tipo pub/sub em que podemos distribuir mensagens para 
    assinantes ao mesmo tempo.

    Pode ser usado em situações como:

        Notificação de múltiplos sistemas em tempo real;
        
        Envio de eventos para diversas filas do SQS, funções 
        Lambda, e-mail e SMS;
        
        Uso em arquiteturas orientadas a eventos, como em 
        microsserviços.

    Para ilustrar melhor, poderíamos usar o SNS para notificar 
    que um pedido foi aprovado, enviando as mensagens para 
    filas separadas, como a de atualização de estoque e de 
    pagamento, por exemplo. Já o SQS é uma fila de mensagens 
    que garante que cada mensagem seja processada pelo menos uma 
    vez e que pode reter mensagens por 1 minuto até 14 dias, 
    diferentemente do SNS pois ele não permite armazenamento e 
    faz entregas em tempo real.

    primeiro milhão de solicitações (requests). Após este 
    valor, há cobranças diferenciadas de acordo com a região 
    da AWS.

            import json
            import boto3
            import os

            def lambda_handler(event, context):
                sns_client = boto3.client("sns", region_name="us-east-1")
                SNS_TOPIC_ARN = os.getenv("SNS_TOPIC_ARN")

                try:
                    if "body" not in event or not event["body"]:
                        return {"statusCode": 400, "body": json.dumps({"error": "Nenhum arquivo enviado"})}

                    pedido = json.loads(event["body"])
                    pedido_id = pedido.get("pedido_id")

                    if not pedido_id:
                        return {"statusCode": 400, "body": json.dumps({"error": "Campo 'pedido_id' é obrigatório"})}

                    # Publica a mensagem no SNS
                    response = sns_client.publish(
                        TopicArn=SNS_TOPIC_ARN,
                        Message=json.dumps(pedido),
                        Subject="Novo Pedido"
                    )

                    return {
                        "statusCode": 200,
                        "body": json.dumps({
                            "message": "Pedido recebido e enviado para processamento",
                            "pedido_id": pedido_id
                        })
                    }
                except Exception as e:
                    return {"statusCode": 500, "body": json.dumps({"error": str(e)})}

          Infraestrutura viva: microsserviços 
        e deploys intelgentes com cloudformation

Os microsserviços são uma abordagem de arquitetura de software onde
uma aplicação é dividida em pequenos serviços independentes, cada 
um com uma funcionalidade específica. Esses serviços podem ser 
desenvolvidos, implantados, escalados e mantidos de forma autônoma,
e que se comunicam entre si através de APIs bem definidas, 
geralmente usando protocolos como HTTP, gRPC ou mensageria.

Com o uso de microsserviços, é possível obter diversas vantagens 
como: 

    Autonomia: cada microsserviço é autônomo e pode ser 
    desenvolvido, testado e implantado de forma independente.
    
    Descentralização: cada microsserviço gerencia seus dados, 
    seja da aplicação ou de um banco de dados.
    
    Escalabilidade e Resiliência: é possível escalar serviços 
    específicos conforme a necessidade, sem ter que escalar toda 
    a aplicação. Além disso, se um microsserviço falhar, parte 
    da aplicação continuará funcionando, sendo necessário 
    realizar uma manutenção apenas no serviço com falha.
    
    Desenvolvido em diferentes tecnologias: cada microsserviço 
    pode ser implementado com a tecnologia ou linguagem de 
    programação desejada.
    
    Conformidade com práticas ágeis: cada equipe pode trabalhar 
    em serviços específicos, sem a necessidade de se preocupar 
    com o desenvolvimento de toda a aplicação.

    Projeto real:

    Contêineres:

        Os contêineres são uma tecnologia de virtualização leve 
        que permite empacotar, distribuir e executar aplicativos 
        de forma isolada, garantindo que eles funcionem de maneira 
        consistente em diferentes ambientes. Ao contrário de 
        máquinas virtuais tradicionais, como no Elastic Compute 
        Cloud (EC2 (Elastic Compute Cloud.)), que virtualiza o 
        hardware, os contêineres compartilham o mesmo sistema 
        operacional, mas isolam os aplicativos em ambientes 
        separados.

        O conceito de contêineres surgiu durante a década de 
        1970 para isolar melhor os códigos de aplicações. No 
        entanto, o conceito se popularizou em 2013 quando o 
        conjunto de produtos de Plataforma como Serviço (PaaS) 
        Docker foi lançado, tornando os contêineres mais fáceis 
        de criar, distribuir e gerenciar, se tornando um padrão 
        na indústria para o desenvolvimento de microsserviços e 
        arquitetura serverless.

        Podemos observar que, uma infraestrutura que utiliza 
        máquinas virtuais (Virtual Machine — VM) em que cada 
        máquina virtual contém seu próprio Sistema Operacional 
        (SO), a aplicação necessária e suas dependências, tendo 
        uma camada intermediária que permite rodar mais de uma 
        VM em uma única máquina. Por necessitarem de um SO 
        isolado, as máquinas virtuais ocupam vários Gigabytes 
        (GBs) de espaço em disco e podem ter um processo de 
        inicialização demorado.

        Em relação a container, é possível observar diversas 
        aplicações, cada uma isolada e que compartilham o kernel 
        do sistema operacional de um hospedeiro. Os contêineres 
        são uma abstração da camada de aplicação que empacota 
        tanto o código quanto suas dependências, e que ocupa menos 
        espaço que as VMs, podendo iniciar rapidamente como 
        processos isolados na máquina do hospedeiro. Portanto, 
        precisam de menos recursos da máquina hospedeira (host).

        Os contêineres facilitam a implantação, pois empacotam 
        todo o código e suas dependências, evitando erros como 
        “funciona na máquina”, mas no servidor de produção, a 
        aplicação não é executada.

        Principais características de contêineres:

            Isolamento: cada contêiner executa um aplicativo de 
            forma independente, sem interferir em outros 
            contêineres ou no sistema operacional host.
            
            Portabilidade: os contêineres podem ser executados 
            em qualquer ambiente que suporte conteinerização 
            (por exemplo: a aplicação Docker), como máquinas 
            locais, servidores de produção ou ambientes de nuvem.
            
            Eficiência: como compartilham o mesmo núcleo do 
            sistema operacional, os contêineres são mais leves e 
            rápidos do que as máquinas virtuais, permitindo mais 
            densidade e melhor utilização de recursos.
            
            Facilidade de gerenciamento: as ferramentas de 
            gerenciamento de contêineres, como o Docker, fornecem 
            uma plataforma para construir, testar e implantar 
            aplicativos de forma mais ágil, facilitando a
            automação de todo o ciclo de desenvolvimento e 
            produção.
            
            Imagens e Dockerfile: os contêineres são criados a 
            partir de imagens, que são especificações estáticas 
            que descrevem o ambiente de execução. Essas imagens 
            são definidas por um arquivo chamado “Dockerfile”, 
            que contém instruções sobre como configurar o 
            contêiner, instalar dependências e executar o 
            aplicativo.

        O uso de contêineres confere as seguintes vantagens:

            Consistência: evita problemas do tipo funcionar 
            somente na máquina, pois o ambiente de execução 
            é o mesmo em qualquer lugar.

            Escalabilidade: é possível replicar contêineres para 
            escalar aplicativos em ambientes distribuídos.

            Segurança: o isolamento ajuda a proteger aplicativos 
            de falhas ou ataques que possam ocorrer em outros 
            contêineres ou no sistema host.

        A AWS oferece o serviço chamado Elastic Container Service 
        (ECS) para hospedar contêineres na nuvem.

    Elastic Container Service (ECS):

        O AWS Elastic Container Service (ECS) é um serviço 
        gerenciado da AWS para executar, gerenciar e escalar 
        contêineres Docker em clusters de servidores. Ele permite 
        que os usuários implantem aplicativos baseados em 
        contêiner sem precisar configurar infraestrutura 
        subjacente complexa. Isto é, o ECS permite executar 
        contêineres Docker de forma nativa.

        Podemos destacar, por exemplo, os seguintes cenários 
        para uso de contêineres na AWS:

            Aplicações web e APIs escaláveis.

            Criação de microsserviços.

        Dentro do ECS podemos executar contêineres das seguintes 
        formas:

            EC2: cria instâncias EC2 para executar contêineres.

            Fargate: serviço gerenciado pela AWS do tipo serverless.

        Embora o Fargate não exija servidores gerenciados pelo 
        usuário (como no modo EC2), ele ainda precisa de um espaço
        lógico para organizar e rastrear os contêineres em 
        execução. Esse espaço lógico é chamado de cluster na AWS. 
        O cluster permite agrupar cargas de trabalho (workloads), 
        monitorar aplicações com geração de logs e facilitar a 
        escalabilidade. No entanto, mesmo requerendo uma 
        configuração inicial de um cluster, o gerenciamento do 
        cluster é realizado pela AWS, sem a necessidade de 
        provisionamento de recursos pelo usuário.

        No AWS Fargate, o cluster é apenas um agrupador lógico, 
        e não um conjunto de servidores. Ele existe para fins 
        organizacionais e de gerenciamento, mas toda a 
        infraestrutura subjacente é gerenciada automaticamente 
        pela AWS.

    Elastic Container Registry (ECR):

        O Amazon Elastic Container Registry (ECR) é um serviço 
        totalmente gerenciado da AWS para armazenar, gerenciar 
        e distribuir imagens de contêiner. Ele funciona como 
        um repositório de imagens compatível com Docker, 
        permitindo que desenvolvedores e equipes implantem 
        aplicações baseadas em contêineres de forma segura e 
        escalável.

        Seus principais recursos são:

            Suporte a imagens Docker e OCI: compatibilidade com 
            imagens de contêineres Docker e imagens do Open 
            Container Initiative (OCI).

            Suporte a CI/CD: permite integração direta com pipelines 
            de implantação com suporte à integração contínua 
            (Continuous Integration — CI) e entrega contínua 
            (Continuous Development — CD).

            Busca de imagens sem servidor: os demais serviços da 
            AWS podem buscar imagens diretamente do ECR sem 
            precisar de servidores adicionais.

            Armazenamento seguro: suporte a autenticação integra 
            via IAM e criptografia automática.

            Versionamento: mantém múltiplas versões de imagens 
            para fácil recuperação.

        O ECR funciona diretamente com o ECS e com funções Lambda.

        No ECR, os desenvolvedores podem criar imagens Docker 
        localmente e enviar (push) para o ECR em repositórios 
        públicos ou privados.

        O ECR é similar ao site Docker Hub que mantém um repositório 
        de imagens públicas e privadas na Internet 
        (https://hub.docker.com/).

        Uma vez que as imagens de contêineres são armazenadas no 
        ECR, é possível versionar as imagens para que possam ser 
        buscadas pelo ECS.

        Na figura anterior podemos ver duas versões de imagens de 
        um contêiner, a data de envio da imagem ao ECR e o tamanho 
        da imagem em Megabytes (MB).

        Para subir imagens Docker em um repositório ECR, é 
        necessário criar um repositório privado ou público e, em 
        seguida, executar uma série de procedimentos, preparando 
        a imagem para ser enviada ao repositório. Os procedimentos
        estão listados a seguir:

            Criar um arquivo Dockerfile: arquivo de configuração 
            usado para definir a imagem de um contêiner Docker. 
            Contém instruções que determinam como o contêiner será 
            configurado, incluindo sistema operacional, bibliotecas e 
            dependências.

            Compilar uma imagem Docker: a partir do comando docker 
            build é possível criar uma imagem Docker para poder 
            subir ao repositório ECS.

            Marcar a imagem com uma tag: o etiquetamento (tag) deve 
            ser feito com o caminho do repositório no ECR com o 
            comando docker tag.

            Autenticar-se no Amazon ECR: para enviar a imagem, é 
            necessário realizar a autenticação no repositório ECR.

            Enviar a imagem para o ECR: por meio do comando docker 
            push é possível enviar a imagem para o ECR.

        Portanto, não é possível executar uma imagem diretamente 
        a partir do ECR. Para isso é preciso criar um agrupamento 
        lógico (cluster) no ECS para então executar as imagens de 
        contêineres.

        Além do ECR, é possível baixar imagens diretamente para o 
        ECS por meio de repositórios públicos na Internet, como o 
        Docker Hub.

    Docker Hub:

        O Docker é um conjunto de produtos do tipo Plataforma 
        como Serviço (PaaS). O principal registro público de 
        contêineres do Docker é o Docker Hub.

        O Docker Hub é um registro de contêineres baseado na 
        nuvem, onde usuários podem armazenar, compartilhar e 
        gerenciar imagens de contêineres Docker. Ele é mantido 
        pela Docker Inc., e é um dos registros de contêiner mais 
        utilizados no mundo.

        Você pode acessar o Docker Hub através do site: https://hub.docker.com
    
        É possível filtrar por nomes de repositórios de parceiros 
        ou por categorias no menu principal do site.

        No docker hub, na suas categorias, selecionamos o menu 
        “Web Servers” para visualizarmos as opções disponíveis 
        de imagens de contêineres, assim como informações de 
        número de downloads (pulls) de uma imagem.

        Iremos usar imagens oriundas do Docker Hub para baixar 
        no ambiente da AWS e executá-las sem nos preocuparmos em 
        configurar servidores.

        A seguir, veremos como construir nossa solução ao qual 
        executaremos uma imagem de contêiner oriunda do Docker 
        Hub.

Criação do Cluster da Solução:

                Infraestrutura como código

Vamos implementar a segunda parte de nossa solução. No entanto, 
iremos subir nossa solução usando infraestrutura como código 
(Infrastructure as Code — IAC).

Para simplificar o processo de criação de tarefas e configuração 
de contêineres, podemos codificar os passos realizados na tarefa 
em um arquivo reprodutível chamado de template. Com o uso de 
templates, é possível definir etapas como a criação de um cluster,
a definição de tarefas e até a configuração de VPCs.

Vejamos como a AWS permite criar templates para implantação de 
serviços, com o serviço do AWS CloudFormation.

Introdução ao Cloudformation:

    O CloudFormation é um serviço que permite configurar a 
    implantação de recursos na AWS a partir de um arquivo de 
    template, que descreve quais e onde os serviços serão 
    implantados. É possível implantar serviços como S3 (Amazon 
    Simple Storage Service.), EC2, RDS (Relational Database 
    Service.), VPC, Elastic Load Balancer (ELB), Lambda, 
    DynamoDB, ECS, além de criação de usuários, roles, políticas 
    de acesso entre outros recursos.

    No arquivo de template é definido uma pilha (stack) de 
    recursos e suas propriedades a serem implantadas.

    EX de estrutura de um template do Cloudformation:

        {
            "AWSTemplateFormatVersion": "data da versão ",
            "Description": "Exemplo de Template",
            "Metadata": { metadados },
            "Rules": { Regras de validação },
            "Parameters": { conjunto de parâmetros},
            "Mappings": {conjunto de mapeamentos },
            "Conditions": { conjunto de condições },
            "Transform": { conjunto de transformações },
            "Resources": { conjunto de recursos },
            "Outputs": { conjunto de saídas }
        }

    No código anterior, podemos visualizar a estrutura de um 
    template do CloudFormation. É importante ressaltar que existe 
    a obrigatoriedade de definir a versão do template e ao menos 
    um recurso a ser implantado. Vejamos o que podemos inserir 
    em cada item:

        AWSTemplateFormatVersion (obrigatório): identifica a 
        versão do template. A última versão é de 09 de setembro 
        de 2010.
        
        Description (opcional): permite definir um texto de até 
        1024 bytes.
        
        Metadata (opcional): define informações adicionais sobre 
        o template ou os recursos a serem instalados, como 
        descrição de uma instância ou de uma base de dados. 
        
        Rules (opcional): valida valores de parâmetros ou um 
        conjunto de parâmetros durante a criação da pilha.
        
        Resources (obrigatório): especifica a pilha de recursos 
        e as propriedades. Por exemplo: EC2, bucket S3 etc.
        
        Parameters (opcional): permite passar valores ao criar ou 
        atualizar uma pilha. Por exemplo: tipo da instância EC2 
        ser implantada.
        
        Mappings (opcional): define conjunto de pares de 
        chave-valor para ajustar configurações. Pode-se mapear 
        tipos de instâncias diferentes do EC2 de acordo com a 
        região de implantação da pilha.
        
        Conditions (opcional): definem recursos ou propriedades 
        com base em condições. Por exemplo, podemos implantar 
        recursos diferentes em ambientes de produção e 
        desenvolvimento com base no valor de um parâmetro de 
        ambiente.
        
        Transform (opcional): podem definir macros simples, como 
        encontrar e substituir textos.
        
        Outputs (opcional): pode definir saídas como o nome do 
        bucket S3 criado na pilha, para facilitar sua busca.

    Depois da implantação da pilha, os recursos estarão disponíveis
    e executando, o que facilita o gerenciamento, pois evita a 
    necessidade de configurar recursos individualmente.

    Além disso, o CloudFormation permite atualizar arquivos de 
    template, para manter um histórico de implantações.

    Após o término da utilização dos recursos, para garantir a 
    remoção de todos os recursos usados em uma pilha, basta 
    excluir a pilha do CloudFormation, e todos os recursos 
    vinculados são automaticamente removidos, facilitando a gestão 
    pelas equipes.

Estrutura da Pilha do CloudFormation:

    É possível utilizar diferentes tipos de formatos para 
    codificar a implantação de recursos. Podemos trabalhar 
    tanto com arquivos JSON ou arquivos YAML. Vejamos a seguir 
    a codificação de um arquivo JSON.

    Código IAC usando JSON:

        {
          "AWSTemplateFormatVersion": "2010-09-09",
          "Resources": {
            "TaskDefinition": {
              "Type": "AWS::ECS::TaskDefinition",
              "Properties": {
                "Family": "td-agriapp",
                "RequiresCompatibilities": [
                  "FARGATE"
                ],
                "Cpu": "256",
                "Memory": "512",
                "NetworkMode": "awsvpc",
                "ExecutionRoleArn": {
                  "Fn::Sub": "arn:aws:iam::${AWS::AccountId}:role/LabRole"
                },
                "TaskRoleArn": {
                  "Fn::Sub": "arn:aws:iam::${AWS::AccountId}:role/LabRole"
                },
                "ContainerDefinitions": [
                  {
                    "Name": "agriapp-container",
                    "Image": "proffernandotfernandes/agriscanner",
                    "Essential": true,
                    "PortMappings": [
                      {
                        "ContainerPort": 80,
                        "Protocol": "tcp"
                      },
                      {
                        "ContainerPort": 5000,
                        "Protocol": "tcp"
                      }
                    ]
                  }
                ]
              }
            }
          }
        }

    Agora vamos ver o mesmo arquivo convertido para YAML.

        AWSTemplateFormatVersion: '2010-09-09'
        Resources:
          TaskDefinition:
            Type: AWS::ECS::TaskDefinition
            Properties:
              Family: td-agriapp
              RequiresCompatibilities:
                - FARGATE
              Cpu: '256'
              Memory: '512'
              NetworkMode: awsvpc
              ExecutionRoleArn: !Sub arn:aws:iam::${AWS::AccountId}:role/LabRole
              TaskRoleArn: !Sub arn:aws:iam::${AWS::AccountId}:role/LabRole
              ContainerDefinitions:
                - Name: agriapp-container
                  Image: proffernandotfernandes/agriscanner
                  Essential: true
                  PortMappings:
                    - ContainerPort: 80
                      Protocol: tcp
                    - ContainerPort: 5000
                      Protocol: tcp

    Perceba que o código é ligeiramente menor, pois não utiliza 
    chaves para agrupar ações relacionadas. Ao invés disso, é 
    utilizada a indentação, que melhora a legibilidade do código.

    Veja que no contêiner, definimos que usaremos a definição de 
    tarefa “td-agriapp” criada anteriormente, parametrizando o 
    “FARGATE” para execução serverless da tarefa.

    Em seguida, devemos definir que iremos utilizar 1/4 de CPU e 
    512 MB de memória. A AWS usa uma configuração em unidades de 
    CPU em vez de GHz. Usamos a função de execução “LabRole” para 
    a execução da tarefa.

    Por último, definimos um nome para o contêiner que será 
    executado, assim como a imagem do contêiner. Neste template, 
    utilizaremos uma imagem pública disponibilizada no Docker 
    Hub no repositório “proffernandotfernandes/agriscanner”.

    Para que seja possível acessar o contêiner, precisamos criar 
    o mapeamento para as portas 80 e 5000 TCP.

Estrutura da aplicação de exemplo:

    A aplicação de exemplo foi desenvolvida em Python, usando um 
    framework web leve denominado flask.

    A aplicação consiste em receber imagens e armazená-las na 
    pasta “static/uploads”. 

    O código da aplicação fica no arquivo “agriapp.py” e o 
    controle de imagens gravadas é feito por meio do sqlite 
    embarcado na aplicação, como no arquivo “database.db”.

    A seguir exibimos o código da aplicação.

    agriapp.py:

        from flask import Flask, request, render_template, redirect, url_for # type:ignore
        import os
        from datetime import datetime
        import sqlite3

        app = Flask(__name__)
        app.config['UPLOAD_FOLDER'] = 'uploads'
        os.makedirs(app.config['UPLOAD_FOLDER'], exist_ok=True)

        def init_db():
            try:
                # Use an absolute path to ensure it’s in the correct directory
                db_path = os.path.join(os.getcwd(), 'database.db')

                conn = sqlite3.connect(db_path)
                cursor = conn.cursor()

                # Create table if not exists
                cursor.execute('''
                    CREATE TABLE IF NOT EXISTS images (
                        id INTEGER PRIMARY KEY AUTOINCREMENT,
                        filename TEXT NOT NULL,
                        date TEXT NOT NULL,
                        latitude REAL NOT NULL,
                        longitude REAL NOT NULL
                    )
                ''')
                conn.commit()
                conn.close()
                print("Banco de dados inicializado e tabela 'images' criada com sucesso!")
            except Exception as e:
                print(f"Erro ao inicializar o banco de dados: {e}")

        @app.route('/')
        def index():
            conn = sqlite3.connect('database.db')
            cursor = conn.cursor()
            cursor.execute('SELECT filename, date, latitude, longitude FROM images ORDER BY date DESC')
            images = cursor.fetchall()
            conn.close()
            return render_template('index.html', images=images)

        @app.route('/upload', methods=['POST'])
        def upload_file():
            if 'image' not in request.files:
                return redirect(request.url)
            file = request.files['image']
            latitude = request.form.get('latitude')
            longitude = request.form.get('longitude')
            if file.filename == '' or not latitude or not longitude:
                return redirect(request.url)

            filename = datetime.now().strftime('%Y%m%d%H%M%S') + '_' + file.filename

            app.config['UPLOAD_FOLDER'] = 'static/uploads'
            os.makedirs(app.config['UPLOAD_FOLDER'], exist_ok=True)

            file_path = os.path.join(app.config['UPLOAD_FOLDER'], filename)
            file.save(file_path)

            conn = sqlite3.connect('database.db')
            cursor = conn.cursor()
            cursor.execute('INSERT INTO images (filename, date, latitude, longitude) VALUES (?, ?, ?, ?)',
                           (filename, datetime.now().isoformat(), latitude, longitude))
            conn.commit()
            conn.close()

            return redirect(url_for('index'))

        @app.before_request
        def before_request():
            init_db()

        if __name__ == '__main__':

            app.run(host='0.0.0.0', port=5000)

            Processamento de linguagem natural

O processamento de linguagem natural é um ramo da Inteligência 
Artificial que permite conferir às máquinas o entendimento de 
linguagens escritas e faladas.

Para isso, são implementadas técnicas de extração de significado 
a partir de textos, reconhecendo regras gramaticais, palavras e 
frases.

Além de melhorar a compreensão de textos, também permite entender 
como as palavras se relacionam em diferentes idiomas e auxiliar 
na desambiguação semântica.

Ao quebrar uma frase, é possível rotular cada elemento em um 
processo conhecido como a etiquetagem (tagging), possibilitando 
a identificação de artigos, adjetivos, substantivos (exemplos: 
nomes, locais etc.), verbos, entre outros elementos de discurso.

Desse modo, é possível identificar ações a serem executadas, como 
verbos em uma frase, permitindo que dispositivos consigam ser 
acionados, como nos assistentes virtuais, por exemplo Alexa e Siri.

Um dos maiores desafios para os sistemas que usavam NLP era a 
falta de precisão e o entendimento do contexto. Porém, esse cenário
vem mudando rapidamente com o surgimento de novas técnicas que 
conseguem entender o contexto com maior precisão.

Nas últimas décadas, com a grande disponibilização de dados e com 
o advento da era do Big Data, surgiram aplicações de NLP em larga 
escala e uso de computação sob demanda, com as novas arquiteturas 
que utilizam o grande poder computacional alinhado com o 
paralelismo para processar simultaneamente grandes volumes de dados.

A AWS oferece soluções que usam NLP para diversos cenários de uso. 
Vale mencionar que as soluções adotam Redes Neurais para melhoria 
de performance. A seguir iremos abordar alguns dos serviços 
oferecidos e seus conceitos.

Amazon Transcribe:

    O Amazon Transcribe é um serviço do tipo Speech-To-Text (STT) 
    que permite a transcrição de áudios e vídeos em textos. Ele 
    utiliza Machine Learning para identificar as palavras e, 
    então, gerar os conteúdos textuais.

    Suas principais características são:

        Reconhecimento de fala: permite converter arquivos de 
        áudio ou streaming em texto.

        Suporte a múltiplos idiomas: transcreve áudio em vários 
        idiomas, incluindo português, inglês, espanhol e francês.

        Suporte a pontuação e formatação: pode adicionar vírgulas, 
        pontos e formatação ao texto gerado para melhoria da 
        legibilidade.

        Identificação de diferentes narradores: permite identificar
        múltiplas pessoas em um áudio.

        Identificação de discursos tóxicos: pode identificar 
        insultos, assédio, discursos de ódio (somente nos Estados 
        Unidos).

        Transcrição médica especializada: realiza a transcrição de 
        falas de médicos e profissionais da saúde (somente nos 
        Estados Unidos).

    Os formatos suportados estão descritos no quadro a seguir.

        x==============x===========================x================x

        | suportados   | Ogg, WebM, WAV            | PCM encoding   |
        x--------------x---------------------------x----------------x
        | Formatos     | FLAC, WAV com codificação |                |

No código anterior utilizamos a classe LabelBinarizer para 
dicotomizar o desfecho, sendo o valor 0 para sentimentos 
negativos e 1 para sentimentos positivos.

Em seguida, criamos uma classe para realizar a remoção de ruídos 
nos dados, como caracteres especiais, pontos de parada e conteúdo 
em html.

Após a limpeza de ruídos, a classe irá transformar as palavras em 
seus radicais, em um processo conhecido como stemming. A seguir, 
vamos ver o que acontecerá com o dataset após o processo de 
limpeza e stemming.

Podemos observar uma mudança no dataset anterior, pois não há 
mais palavras de ligação (exemplo: of, the, a, entre outros), 
pois foram removidos durante o processo de limpeza de dados e 
do processo de stemming.

Agora iremos preparar um pipeline, onde automatizaremos todo o 
processo de limpeza de dados.

O pipeline irá definir etapas como limpeza de dados, vetorização 
e treinamento do modelo. No processo de limpeza de dados, será 
chamada a classe “TextCleaner” ao qual criamos para remover os 
ruídos nos dados e realizar o stemming.

Para a vetorização, utilizaremos a classe “CountVectorizer” que 
transforma cada sentença em um conjunto de palavras soltas, com 
a contagem de suas frequências, criando o que chamamos de Bag of 
Words (BoW).

Por último, usamos a classe LogisticRegression para treinar o 
nosso modelo preditivo.

    %%time
    #Criando o pipeline completo
    pipeline = Pipeline([
        ('limpeza', TextCleaner()),
        ('vetorizacao', CountVectorizer(min_df=0.0, max_df=1.0, binary=False, ngram_range=(1,3))),
        ('classificador', LogisticRegression(max_iter=500, random_state=42))
    ])

O código anterior cria o pipeline de transformação e classificação
dos dados para que seja utilizado para treinamento do modelo e, 
em seguida, para realizar novas predições. Agora, precisamos 
aplicar o pipeline em nossos dados.

    %%time
    # Treinamento do pipeline
    pipeline.fit(train_reviews, train_sentiments_bin)

    # Avaliação do pipeline
    predictions = pipeline.predict(test_reviews)
    acc = accuracy_score(test_sentiments_bin, predictions)
    print("Acurácia do modelo:", acc)
    # Acurácia do modelo: 0.8964

Observe o código completo:

    %%time
    import pandas as pd
    import numpy as np
    import nltk
    import re
    from bs4 import BeautifulSoup
    from nltk.tokenize.toktok import ToktokTokenizer
    from nltk.corpus import stopwords
    from sklearn.pipeline import Pipeline
    from sklearn.feature_extraction.text import CountVectorizer
    from sklearn.linear_model import LogisticRegression
    from sklearn.base import BaseEstimator, TransformerMixin
    from sklearn.preprocessing import LabelBinarizer
    from sklearn.metrics import accuracy_score
    #importação das stopwords
    nltk.download('stopwords')
    # Leitura dos dados
    imdb_data = pd.read_csv('IMDB Dataset.csv')
    print(imdb_data.shape)
    imdb_data.head(10)
    # Divisão do conjunto de dados
    train_reviews = imdb_data.review[:40000]
    train_sentiments = imdb_data.sentiment[:40000]

    test_reviews = imdb_data.review[40000:]
    test_sentiments = imdb_data.sentiment[40000:]

    # Transformar os labels em 0 (negativo) e 1 (positivo)
    lb = LabelBinarizer()
    train_sentiments_bin = lb.fit_transform(train_sentiments)
    test_sentiments_bin = lb.transform(test_sentiments)

    # Lista de stopwords
    stopword_list = stopwords.words('english')
    tokenizer = ToktokTokenizer()

    # Transformer personalizado para pré-processamento
    class TextCleaner(BaseEstimator, TransformerMixin):
        def __init__(self):
            self.ps = nltk.PorterStemmer()

        def remover_html(self, text):
            soup = BeautifulSoup(text, "html.parser")
            return soup.get_text()

        def remover_conteudo_colchetes(self, text):
            return re.sub('\[[^]]*\]', '', text)

        def remover_caracteres_especial(self, text):
            pattern = r'[^a-zA-Z0-9\s]'
            return re.sub(pattern, '', text)

        def remover_stopwords(self, text):
            tokens = tokenizer.tokenize(text)
            tokens = [token.strip() for token in tokens]
            filtered_tokens = [token for token in tokens if token.lower() not in stopword_list]
            return ' '.join(filtered_tokens)

        def stemming(self, text):
            return ' '.join([self.ps.stem(word) for word in text.split()])

        def clean_text(self, text):
            text = self.remover_html(text)
            text = self.remover_conteudo_colchetes(text)
            text = self.remover_caracteres_especial(text)
            text = self.remover_stopwords(text)
            text = self.stemming(text)
            return text

        def fit(self, X, y=None):
            return self

        def transform(self, X, y=None):
            return X.apply(self.clean_text)

    # Criando o pipeline completo
    pipeline = Pipeline([
        ('limpeza', TextCleaner()),
        ('vetorizacao', CountVectorizer(min_df=0.0, max_df=1.0, binary=False, ngram_range=(1,3))),
        ('classificador', LogisticRegression(max_iter=500, random_state=42))
    ])

    # Treinamento do pipeline
    pipeline.fit(train_reviews, train_sentiments_bin)

    # Avaliação do pipeline
    predictions = pipeline.predict(test_reviews)
    acc = accuracy_score(test_sentiments_bin, predictions)
    print("Acurácia do modelo:", acc)
    # --- Nova review positiva para teste ---
    new_review = ["The Lord of the Rings was awesome, I´ve never seen such an amazing movie!"]

    # Previsão do sentimento da nova review
    pred_new = pipeline.predict(pd.Series(new_review))

    #Transforma a predição de 0 em negativo e 1 em positivo
    pred_label = lb.inverse_transform(pred_new)
    print("Sentimento da nova review:", pred_label[0])
    # Sentimento da nova review: positive
